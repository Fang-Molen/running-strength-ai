# V74 UI 集成与修复记录

本轮采用用户上传的四份 V74 包作为最新页面与资源来源，以上一轮已修复的本地 R4/健康核心作为逻辑基线。两者不是覆盖关系：新页面覆盖旧页面，最新安全、离线复盘、事件和健康事实逻辑保留并逐项适配。用户手机 V70 未被访问或修改。本文仅说明本轮；旧版本目录中的验收数字都是历史记录。

## 实际修复

- 保留 R4 的教练入口/面板与离线复盘，适配 V74 热身、训练编辑和保存流程，避免用旧分支的大脑覆盖较新的修复。
- 补回饮食页使用的 BODYLAB `Model` 导出，消除页面运行时错误；与动作演示共用配套人物。
- 男女模型离线加载、动作分解、视角和慢放、加载失败重试，支持显式下载动作资源。
- 体重未知仍可查看通用模型；外形和测量值分离，男女参考外形分别保存。去掉“女性模型未提供”旧占位。没有制作与原插图一模一样的脸型。
- 饮食旧 `carbs` 与新 `carb` 兼容；真实零值和未知值区分；移除打开页面时改写旧食物的自动迁移。全部旧记录保留，不截断到 200 条。
- 食物修改、删除、批量添加使用既有事件写入；按运动员隔离；损坏/满额存储不得显示成功。日程保存失败时不先更新界面或继续写日志。
- 恢复已加固的设备导入边界：未知运动类型不凭距离猜测；不把活动条数当课次数；不按接近的时间/距离合并不同来源活动。
- 能力图使用已有五维事实与可比变化；无核准常模不显示经验 0–100 分，恢复和执行独立展示。
- 两次未完成课程不足以诊断能力不足；缺少实际时长不借用计划时长。保留安全转诊，问答不升级为自动加量建议。
- Service Worker 缓存版本及资源策略同步，允许本地动作 GLB/字典和食物库缓存，禁止 API、授权请求、导出包进入该缓存。

## 测试失败的处理方式

首次完整回归日志保留，未把失败从日志中删除。部分断言明确描述旧产品状态，需要随已授权的新需求更新，而不是放宽业务约束：

- 原缓存测试写死旧版本名，更新为本轮版本，并新增真实 GLB 离线请求和 API 排除断言。
- 原动作资源测试写死旧动作哈希，使用 V74 来源的实际哈希；继续校验原始 human.glb 不变、53 骨骼、4 个变形通道、76 个动作 ID 和所有缓存资源存在。
- 原人物测试要求“女性模型尚未提供”/“定制3D尚未完成”文案，改为检查可调画布、男女入口和“未还原原设计脸型、非实测体型”的明确限制。
- 原能力测试将完成频次换算经验分，改为检查五维事实、缺失值与不输出未经核准评分。
- 原知识包测试要求下一课删除跑步明细，与 V74 K15“下一课建议保留实测及必要安全来源”合同冲突。更新为明确检查实际跑步证据和每项必需安全来源保留；饮食问题仍不混入无关跑步明细。
- 原品牌静态测试禁止源码出现 Garmin 字符串，与用户授权的 Garmin 只读导入冲突。改为禁止 Garmin 专属训练写入/导出函数，保持已有引用及预算检查。
- 部分导入用例的当天 10:00 时间在运行时仍是未来，改为合成当天 00:00，不改变“未来记录不得进入当前事实”的断言。
- 浏览器脚本的按钮名随 V74 导航变化更新；脚本失败和真实页面错误分别记录。

最终结果以同目录验收结果与实际日志为准，不把首次失败或中途定向通过写成整体通过。

浏览器发现并修复的性能问题：3D 暂停仍逐帧蒙皮和绘制，导致软件 GPU 环境中截图/操作超时。动作台暂停时改为视角、大小、材质变化才重绘；播放上限 30 fps，隐藏页面暂停推进。体型台静止时也按需绘制。仍须在用户真实 iPhone 上核验帧率、发热及 WebGL 内存，本地桌面模拟不代表真机结果。

- 新主页不再在服务端首屏展示旧体重/日志占位，水合测试保留“有本地数据与没有本地数据首帧字节完全一致”的核心断言，检查新版未就绪标记和日程占位。
- 新动作详情复用图示、目标肌群和说明区，原测试“完全没有 SVG/图片且步骤尚未补齐”不再适用；改为检查已有动作步骤、审校限制、无远端嵌入及无自动写计划控件。原始事实层和保存失败断言不变。

构建后浏览器发现首次 Service Worker 接管可能打断刚发生的页面切换。现等待实际 controller 再预缓存，移除 V74 新增的无条件 controllerchange 强制刷新分支，避免它绕过正在训练的保护。更新后的页面在用户下一次刷新/重开时加载，不主动刷新正在操作的页面。配套动作镜头增加少量留白，改善脚部贴边。

构建版刷新检查的等待上限曾为 25–30 秒；在本地全量回归并行时页面初始化超过该值。单独诊断确认实际能完成重新就绪，未出现未捕获异常。浏览器脚本把“页面就绪”的等待上限改为 120 秒，数据、模型加载、保存等结果断言不变。此前超时日志保留。当前主包较大，首开/刷新性能与真实手机负载仍需单独优化和实机测试，不能把本地功能通过当作移动端性能达标。

最后的 R189 资源用例仍限定单一 human.glb 和旧懒加载文件位置，已核对为版本合同变化：继续验证模型白名单、本地资源、全部动作帧、无外部模型 URL、无自动缓存下载；懒加载检查移至实际入口 `exercise-editor`。同时修复 `muscle-explorer` 与 `fuel-guide` 的静态引用，使动作/体型组件能延后加载，并移除共享动作入口中残留的旧 FormFigure 备用人物。26 项相关定向测试通过后，再次执行完整 npm test；不把此前 npm test 的失败退出码当成通过。

3D 冷加载诊断：两个模型在本地软件 GPU 上首次加载/绘制分别约 34.6 秒、29.9 秒（原始结果 `model-diagnostic-final.log`），并行测试下曾超过原 45 秒资源超时。修复为加载期间立即显示标注清楚的可操作二维备用示意，3D 工作仍有 90 秒上限；离开时取消、失败后可重试，不影响保存或教练安全逻辑。人物页采用同样上限，浏览器等待覆盖该产品上限。没有删除冷加载失败记录，也未把备用二维当作 3D 加载成功；最终仍断言男女3D实际就绪和姿态改变后的像素差异。

最终验证顺序说明：完整单元回归通过后，仅对3D冷加载上限及备用提示做了性能降级处理；这部分用最终类型检查、构建和真实浏览器男女模型/姿态像素/离线重开复验。未再次重复跑没有逻辑变化的整套训练大脑测试，也未把定向几何或浏览器检查累加为单元用例。

后续缓存诊断进一步定位冷加载延迟：相同 5,382,588 字节模型，在本地预览服务开启内容压缩时 curl 耗时 30.296 秒，identity 响应仅 0.092 秒；浏览器 fetch 约 29 秒，实际 Cache.put 约 54 毫秒。因此不能将此前冷加载延迟全部归因于软件 GPU。`preview-compression-comparison.json` 和逐资源 `cache-diagnostic` 保留原始证据。未改动平台服务；27 项离线资源下载的浏览器等待窗口改为 300 秒，模型就绪、缓存完整性、真实离线重开等断言保持不变。首次下载性能仍列为限制，不等同真机性能通过。
