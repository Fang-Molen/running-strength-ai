一 目标与实施原则
最终目标：方坤能够长期认识同一位运动员，基于有效记录理解问题、分析训练、结合目标统筹跑步力量饮食与恢复、生成近期及长期阶段安排，并在新证据出现后解释和修正判断。用户能够知道依据、修改范围、未确定部分与何时复查。
1. 保留已有能力：复用训练记录、有效画像、同协议比较、R5、周期草案、确认撤销与本地规则；首周确认和既有正式计划继续受保护。
2. 先可靠再扩展：恢复回执和完整备份可与正常问答误拦修复并行；共同事实与限制合同稳定后，继续提升画像与计划。
3. 联网一直放开，模型参与教练判断：正常问答默认自动调用联网模型，模型结合相关资料分析原因、比较解释并提出可执行的训练候选；本地计算、事实版本和有效限制为判断提供依据。一次设置后连续问答不逐条确认、不因关键词或资料未知转为强制本地；若用户自行关闭联网或服务实际故障，才按对应状态处理。模型不直接修改正式计划。
4. 历史与事实不可混：目标不覆盖测量，计划不冒充完成；记录更正后保留历史，受影响结论以来源版本复核并更新或撤回。
5. 风险约束按任务作用：允许安全知识、记录查看和资料纠正；冲突训练候选继续受有效限制约束。未知不等于正常或医疗许可。
6. 提案与执行分开：生成候选不等于改课；在当前项目边界下，正式计划变动经过预览、版本核验、确认和可审计回执。不得让模型直接写计划或声称已完成未执行的操作。
7. 科学与工程分别验收：源码测试可验证执行行为；个体剂量、专项、恢复和特殊营养规则需要按适用人群独立审查，不能把通过测试当作临床或训练效果证据。

三 共用合同与跨模块约束
3 1 一份有效事实 多份用途解释
沿用现有事件、更正、有效画像和来源过滤。每个事实至少能追溯人物、来源、发生时间、记录时间、修订、单位、确认状态及可比协议。新测量、更正历史、修改目标、删除与撤销采用不同操作。按事实来源修订检查派生结论；过期或无法确认时标待重审，不把旧判断显示为当前。
为防补偿队列和失效标记本身写失败，读取判断时仍比对其依赖的持久事实版本；若证据缺失、不可读或版本不一致，不能展示为新结论，之后可从已持久事实及更正记录幂等重建。
3 2 短期执行与长期方向
目标、阶段、周、单课、实际完成和反馈分别保留版本；远期是条件草案，现有实现只允许首周确认；未来扩大一次确认范围是产品能力设计，任何正式写入仍需要范围、版本、限制检查及可撤销回执。更正或目标改变只重新审视受影响候选；已执行事实和独立限制不被悄悄覆盖。
3 3 同意 预算与故障
联网默认长期开启，当前用户连续正常问答自动使用本人本次问题相关的训练、目标及恢复等资料，不逐轮弹确认；设置里可查看使用范围并自主关闭。服务端自动处理用户身份、请求快照、版本和计费，不让这些技术步骤变成日常操作关卡。资料变化或切换人物时标记相关结果过期；未同步的离线变化不能伪装成服务端已核验。区分未发送、已派发、已返回和状态未知；已派发且结果不明时先查请求和账本，不盲目重复收费。
3 4 功能现有状态的识别
“已有”表示源码可见，“本次复现”表示合成数据触发，“拟议”表示待开发，“待核”表示真实设备、账号、发布或专业效果没有证据。目标阶段没有承诺日期或训练结果；真实发布和使用的前置条件单列，不把条件当成已验证。

B05/B06/B07 可恢复性设计（拟议，B05原则已确认）
当前证据和约束
已有：bulk-store.ts 大键先更新内存再排队异步写 IDB，失败可尝试 localStorage，双失败只留内存并置 PERSIST_FAILED；flushBulkStore 不会向调用者传递已吞掉的错误。小键在 localStorage，vault.ts 另异步镜像 IDB；恢复预检和同步逐项回退已存在。settings-center.tsx 在同步返回后 600ms reload。合成故障已经复现两层均写失败却返回成功；删除广播也复现缓存残留。当前 vault 导出不限大小，导入单项大于 5,000,000 字符跳过、文件超过 30,000,000 字节拒绝。待核：真实浏览器配额、系统清理、真机断电及全入口并发。IDB 事务只能覆盖同一数据库中指定 object stores；不同数据库、localStorage 和内存之间没有原子提交。
入口、预检和隔离
统一文件、自动快照、旧格式和计划文件恢复入口；先解析版本/格式/完整性及逐项类型、键许可、凭据剔除、人物归属、大小、重复键、迁移兼容、存储可用性并列出新增/覆盖/相同/跳过、容量需求及风险；不受支持的未来版本、坏哈希、无法识别、目标存储不可读或容量不足均在写入前拒绝。全部备份必须零非预期跳过；受限文件明确范围及逐项跳过，不得显示完整恢复。备份中没有的项目保留，凭据不导入。
恢复必须经全应用协调器获取跨标签排他锁，并在恢复前先阻断所有参与写入者、导入、自动同步、镜像、迁移、后台任务，等待已有异步队列真实结束并检查结果；其他标签进入只读恢复态并确认暂停。锁必须覆盖常规写入，不只是恢复入口，标签新打开也要先查持久恢复状态。使用 Web Locks + 持久恢复状态/代次和 BroadcastChannel/storage 通知；旧版本页面不遵守新锁、可能静默或被冻结后恢复，广播无响应、标签枚举或等待超时都不能证明其已停止写入。必须先验证全部写者及旧版缓存被强制升级或中止；做不到时禁止原地覆盖恢复，保留原始数据，提供新来源隔离导入的候选路径。隔离导入本身不能保证旧页面停写，切换前仍需对来源快照与差异复核，并让用户确认切换范围；无法保证快照一致时仅作为待核副本。锁不可用或任何条件不可证明时，不声称隔离成立。外部脚本、浏览器清理、旧版本不配合或绕过协调器时无法保证隔离；测试与发布时必须清点所有直写点。锁只用于互斥，不替代持久日志。预检到确认之间检查人物与目标键版本/哈希，变化则重新预检。
可实现的恢复日志及步骤
建议新增独立 restore-journal IDB：operation {id, format, manifestHash, phase, generation, owner, createdAt, keys, failure}，entry {key, backend, beforePresent, beforeBytes/hash, targetBytes/hash, stage, writeReceipt, rollbackReceipt}。对每个逻辑键的每个物理位置分别记录 before、target、是否缺失、来源与哈希，包括localStorage、bulk IDB、vault镜像及pinned/fallback/迁移标记；旧值分块保存，不能只保存一个内存值。恢复意图和读回回执亦按物理位置记录。日志及旧值写入后等待 IDB 事务 complete，再从新事务逐块读回并核对字节/哈希和清单。无法持久创建或读回完整回退资料，即停止且目标未改。预估剩余空间仅用于提前拒绝，不能保证配额，实际写入失败仍需处理。
1. 执行 prepareRestore(file) -> plan：预检并建立不可变目标清单与值，按支持的格式流式或分块读取；申请锁、排空队列、核对当前版本。然后完整备份每个受影响键的旧值和所有将改变的镜像/标志，写入持久日志并验证。标 PREPARED，此之前不修改目标。
2. 持久标 APPLYING 后逐项处理，先持久 writeIntent（包含旧值/目标哈希/目标后端），再对对应权威存储执行写/删，等待实际 IDB transaction complete 或 localStorage set/remove 正常返回，随后绕过内存从对应持久后端重新读值/缺失并核对；小键保险箱镜像也要显式等待写入及读回，不依赖现有吞错的猴补丁。每项持久记录已验证回执；若回执写失败，视为中断，不把该项当作未写。恢复过程中禁止 IDB 失败后隐式切换 localStorage，除非预检明确该键的后端且相应旧值/回退均已记录。预留空间不能保证写入或回退成功。
3. 全部目标及受影响镜像重新从持久后端核对，包括新增、覆盖、相同、墓碑和未被覆盖的约束；持久写入 COMMITTED 是不可逆的提交点。只有能从日志持久读回并核实 COMMITTED，才允许提示成功。提交点后重建内存和广播；缓存或广播失败标记待修复并重试，不自动回滚已提交数据。若提交写入或读回结果不确定，先重读权威日志判定：已提交则保留结果并完成缓存修复；已确认未提交才可进入回退；日志不可读、标记矛盾或无法判定时进入只读受限状态，不能猜测回滚或成功。请求浏览器持久存储可减少清理风险，但 transaction complete + 独立读回不是对断电、设备损坏或浏览器驱逐的永久保证；明确设备级边界。
4. 在能确认尚未提交 COMMITTED 时，失败可持久标 ROLLING_BACK，逆序从已验证旧值逐项恢复原后端和镜像，逐项等待提交、重新读取校验并持久回执；原先缺失则删除。因崩溃可能目标已写但回执未写，所有有 intent 的键均检查当前权威持久值：对权威值、每份镜像及元数据逐位置比较：若为目标则回退，若为旧值仅标该位置已恢复；两者均非则记录冲突、停止自动覆盖并保留备份。不能仅凭主值已恢复推断镜像一致，所有位置均读回后才算回退完成。受支持隔离内其他写者被阻止，仍不能假定外部不可能更改。
5. 全部回退及镜像读回一致才记 ROLLED_BACK 并恢复正常使用；若配额、IDB 不可用、回退写或日志失败，记 RECOVERY_REQUIRED（若日志本身不可写，保留最后可读的非终态），逐项列出已恢复、待恢复、冲突与不可读取；保持写入封锁，保留日志和旧值，不显示“原有记录全部还在”。允许用户恢复存储后重试，或导出可读的恢复包；不能承诺所有故障一定能自动回退。
6. 启动时必须在 activateBulkStore、initVault 的迁移、镜像回填及应用正常读写之前先检查持久恢复标记与日志；同时设置初始化标识，确认两个可持久位置的恢复代次和状态一致，标记缺失、互相矛盾或日志损坏且存在旧数据时禁写并提供人工恢复/可读导出，不能把日志为空自动当作新安装。PREPARING未完成且无法证明没有修改目标时进入恢复受限态；COMMITTED后复验不一致同样进入受限态；未完成的 PREPARED 若无写入意图可安全终止，APPLYING 或 ROLLING_BACK 默认继续回退，按上述旧/目标/第三值识别处理；COMMITTED 验证持久数据和回执后重建缓存、解锁。日志库打不开、意图不完整或读回不确定时进入恢复受限界面，不能按空库初始化或自动覆盖。中断后的锁会释放；已改造且遵守协议的标签必须检查持久状态并停止写入。旧版或绕过协议的标签无法依靠该标记阻止，只有验证全部写者受控后才能原地恢复。终态清理应延后。设备内回退日志只能用于本机故障恢复，不能替代设备外备份；外部备份需明确覆盖范围、由用户保存并重新选择文件核验，浏览器发起下载本身不证明保存成功。设备整体清理或损坏导致标记和日志同时消失时，系统可能无法识别先前中断，依靠经验证的设备外备份恢复；不承诺自动找回。
接口示意：durableStore.read(key, backend) / write(key, value, expectedRevision) -> receipt / remove，明确 IDB complete、localStorage 写入与镜像确认的不同语义；restore.prepare / restore.commit / restore.recover 返回 operationId, overall, perKey[{write,verify,rollback,error}]，全部 Promise，底层拒绝传播，不能以 getItem 读内存或当前 flushBulkStore() 当作持久证明。恢复提供“完成”“未开始”“已验证回退”“需要处理”四种结果；只在完整验证后说成功。预检之后停止文件不可读或目标改变也不得动数据。
备份容量、格式与删除一致性
统一导出/导入规格：新版本采用分块记录及 manifest，包含格式、schema、清单、每键字节数与哈希、分块顺序/总数、明确包含与排除范围；导入按块验证且可恢复单键超过 500 万字符及总量超过 30MB，不能先以旧限制拒绝。浏览器文件读取、内存及目标后端大小仍可能限制：用流式读写和增量校验减少内存，不声称无限容量；若当前环境做不到完整往返，导出前明确拒绝“完整备份”或提供明确列明缺项的受限备份，不可事后才发现。旧 JSON 保留兼容入口；旧大文件可采用流式解析或明确无法支持、禁止冒称已完整导入；禁止只因超限跳过却报完整成功。新格式发布前实际测试 5,000,001 字符单键、总量 >30MB、Unicode 字节与字符差异及新设备往返。只要应用当前数据超出可恢复合同，不得生成标为完整的备份；下载触发不是文件真正保存成功的证据。
B07 拟议：先将该数据家族的所有有效写入统一收口，在同一可串行化协调机制下将值、修订和墓碑放入同一权威IDB事务；localStorage现有同步直写无法与独立IDB版本原子提交，迁移前必须盘点并改造所有写者/镜像/标记，不能只补版本号。尚无法改造的家族继续保守隔离，冲突时禁止自动覆盖，不宣称已全局保证。修订由事务内单调分配，提交完成后广播 {key, revision, op}；接收后从持久层读取（含不存在），带版本比较并清除缓存，不能让晚到的旧读覆盖新版本；广播丢失时重启或激活页面重新同步。跨标签写、删除、恢复共享锁和版本协议，迁移/降级/镜像都应参与；浏览器之外的跨设备同步另行设计，不能混称。

D01 联网主链与真实服务就绪
当前融合版先给本地答案、逐次同意、创建快照后才允许联网；部分问题先被R5直接return，旧疼痛或安全状态也可全局阻断联网。新目标为：用户发送正常问题→并行解析问题及读取相关事实→后台自动建立或复用安全身份与请求快照→自动调用联网模型→校验事实并展示分析。一次设置后连续提问无需重复点击；本地计算协助而非替代模型。
保留真实服务端身份和资料归属，自动续期及准备快照；不能通过假账号、开发测试身份或关闭鉴权假装成功。状态配置检查不证明模型、登录和预算可用。若真实服务、身份或额度不可用，显示准确原因和标为本地的有限回答，不能把本地规则伪装成联网模型；服务恢复后新问题自动重试联网。
用户本轮已明确本人教练问答联网常开；把相关训练、目标、恢复等资料用于本人所提教练问题作为既定用途，不再每轮追问相同许可。只纳入当前任务相关的本人有效资料；可在设置查看、更改或关闭。不把这一偏好扩展为无限收费、对外共享其他人资料或模型直接改正式计划。
D02 两端校验改成按断言分类
前端和服务端统一版本化合同：个人事实绑定本人来源、修订和单位；计算值由确定性代码重算；一般教育数字和条件性建议不要求在个人历史中原样出现；个人训练建议注明目标、依据与适用条件；训练放行、诊断、修改成功声明另作判断。
普通数字、否定句或“导致、引起”等词不得触发整段拦截。发现个别事实错漏时优先更正或标注该片段，保留可用分析和下步建议；无法可靠纠正时明确不确定和局部限制，而不是用统一“未通过”吞掉全部回答。高风险的明确伤害性放行、伪造个人事实或虚假写入不能被当作可靠结果；前后端共同回归，不靠单独关闭一个前端开关。
D03 深度教练判断与候选计划
联网模型承担正常教练问题的综合分析：围绕目标、训练结构、配速或重量、恢复与历史表现，比较可能原因及反证，提出条件性倾向、可执行候选、替代方案和复查点。它可以生成短周期和长期阶段草案，也可以指出已有方案的问题；数据不足先解释已知部分并只补最影响决定的关键项，不能反复用“资料不足”搪塞。
本地计算提供可追溯数字和版本；模型提出的建议是建议，并非历史事实；正式计划修改须具体预览、确认、冲突检查和持久回执。既有项目禁用模型直接写计划和虚报已保存的边界保持不变。
D04 联网上下文与长期画像
现链仅发近14天最多6条本人MANUAL/APP标量，不发完整分段、组次、饮食、正式计划或历史会话；旧helper内容不等于当前主链已发送。新设计按问题自动选择必要的、与当前人物相关的目标和赛期、长期与近期可比训练、分段和力量组次、恢复、饮食及相关已确认计划，保留来源、时间、修订与缺项。较长历史先生成可追溯摘要，关键原始记录按需回查，不能固定14天上限或默认把全库上传。
聊天的连续追问复用同一人物的有效事实与对话上下文；新训练或用户更正时，使受影响画像和解释待重审并更新。分析中使用的本人事实、模型推测与未来建议必须区分。是否检索最新网页是另一项能力：有检索才说明来源和日期；仅调用联网模型不能宣称查过网页。
D05、D07、H04 语义与风险分流
修复 R5 先于后层解析的问题。对照真实发送入口：①“我没有腿疼，解释一下RPE”和“我没有疼痛，解释一下RPE”均回答知识，不产生症状追问；②“不是没有腿疼”识别肯定；③“没有胸痛但腿正在疼”分别识别否定胸痛和肯定腿疼；④“昨天腿疼，现在完全不疼了，解释一下RPE”分别保留历史和当前时态，可答知识但不自动解除旧限制；⑤“朋友腿疼，我想了解RPE”不写成本人症状；⑥“不用保存，只解释”不写入；⑦当前肯定症状与知识共存时，先安全处理，再回答不冲突部分。覆盖不确定、假设、否定跨子句、反问及未指明主体；歧义进入澄清而非推断安全。以上要测 coach-sheet.tsx 实际送出行为，不能仅测 detectRedFlags。
coach-red-flags.ts 的 ENERGY 不应凭“控制体重”单词升级。普通控重问题答一般知识或补背景；明确极端限制摄入或相关异常症状依据经专业审核的规则升级，保留危险证据与时间、主体，不简单删除 ENERGY 保护。以本次“我想控制体重，如何合理安排饮食？”错误 MEDICAL_REVIEW 为反例，以明确危险行为/异常症状为正对照，新增专业审核与误报、漏报回归。症状和剂量规则逐条说明适用对象、证据和失效条件，由专业人员及工程分别审阅。
D08 区分因果、诊断、放行和写入
拆开 analysis-reply-validation.ts 的合并错误：一般原理按内容和证据审核，不因“引起/导致/造成”自动拒绝；个人因果缺证据时保留事实、明确可能性及替代解释，不得确诊；个人诊断、无权限医学放行、声称已经修改或解除限制分别处理。不得简单删除关键词规则而让危险表达穿透；否定的写入声称也应正确识别。
回归：本次“力量训练会引起肌肉适应”当前误拒，应允许一般教育；“缺乏睡眠可能导致疲劳”继续允许；“你的HRV下降证明某病/肯定由某因素造成”降级或拒绝；“没有疼痛的情况下，可以恢复训练”不能借无痛放行；“我没有修改计划”不得误当已经写入；“我已替你改计划/解除限制”无宿主事实和权限时拒绝。服务器和客户端对同一策略分类一致，必要时保留已验证部分并解释被移除内容。
D09 阶段、核验和费用诊断
建议内部响应提供 stage、稳定错误类别、dispatchState（NOT_SENT、DISPATCHED、RETURNED、UNKNOWN）、策略版本和不含敏感原文的 trace ID；费用另以账本标记未预留、已预留、已结算或待核，不能把已返回后被拒称未调用或一概声称未收费。用户界面用简明原因和下一步：配置不可用、未登录/身份错误、快照过期/撤销、预算不足、超时且结果未知、服务端输出拒绝、客户端安全拒绝分别显示；保留本地结果，不自动重试可能收费的请求。内部日志不记录密钥或不必要的健康原文。
coach-online-request.tsx 的 MODEL 一律“通过事实与安全格式核验”与 coach-sheet.tsx 的“未经核验”冲突，应改为分别描述已执行的格式/规则检查与未完成的事实或专业核验；unverified=true 绝不同时声称事实已核验。测试覆盖配置、401、快照过期、额度、上游超时、服务端数字拒绝、客户端因果拒绝、授权变化及删除失败；断言真实调用状态、账本状态与 UI 不矛盾，超时不自动重复扣费。
联网常开 深度教练与防误拦详细设计
本节依据本次明确要求，修订联网与模型定位。用户已明确要求联网默认一直放开、正常问题直接联网分析，不逐次弹同意；并授权本人教练数据用于所请求的联网问答。这一授权是本方案的产品输入，不再要求用户逐轮批准或把同意状态不明当作常态。应提供一次可查看的说明、清晰开关及撤回，不能把说明做成每次使用的关卡。此处授权覆盖所请求教练问答所需的本人资料及相关模型服务；正式计划写入、超出该用途的共享或其他人的数据不由此自动授权。服务提供方、发送类别、保留期限、费用和设置需真实展示；不能凭空宣称某项部署或费用已经获得验证。
一、现状与必须纠正的表述
src/lib/coach/online-session.ts 的当前主链仅选择近 14 天、最多 6 条本人 MANUAL/APP 符合条件的记录中的标量；不是完整训练、力量组次、饮食、设备分段、正式计划或历史对话。旧 online-coach.ts 的丰富事实包不能视为当前新链已发送。客户端对 HOLD_ACTIVE/ESCALATION_REQUIRED 在准备阶段全局中断，当前每轮明确同意、创建快照后调用、结束撤销。
server/coach-deepseek/coach-snapshot-store.server.ts 当前每个快照创建独立同意和随机 sourceVersion，同时推进主体唯一 source_version；创建第二个快照可能使前一个不再可读。迁移 002_coach_snapshots.sql 将 consent_id 设为 UNIQUE，不能原样表示一个持续授权下的多个快照；当前删除快照实为撤销关联同意。001_deepseek_budget.sql 提供预算和预留表，但迁移声明未执行，不能断言真实环境可用。
前次问答审计中的 A01–A08 显示否定、无约束、旧限制、普通控重、一般因果和数字可能被误拦；服务端和客户端均需一致修复。GET configured 仅说明配置检查，不证明真实连接、身份、余额及结算。
相较上一版方案，将“模型可选增强”“无持续授权时保持每次确认”和“模型候选范围仍待用户决定”调整为：在线模型是正常深度教练判断的主要组成部分；联网默认启用并自动调用，覆盖本次已授权问答及数据；本地计算、安全规则和可追溯校验配合模型，而不是把模型限制为可选润色。这不意味着模型可直接提交正式计划。是否可实际调用取决于真实服务配置及运行状态，不以愿景替代实现。
二、请求流程与三种权限
1. 用户提交问题后立即显示处理中；默认联网开关开启时，不出现逐轮许可框。解析问题、有效事实和限制，按任务选择资料；服务端验证已绑定的用户或设备身份，创建请求快照、处理计费并调用模型。身份初始化或会话恢复由系统处理，不要求每条消息登录。首次及迁移说明可在设置中查看，不要求每轮操作。本次指令确定该用户的产品目标；实际账户和设备完成真实绑定后建立可撤销设置记录，不能凭空假定旧服务器已有账户或为其他用户伪造同意。
2. 一般原理、普通控重、数据解释、训练复盘和候选方案正常走在线分析。未记录风险是“未知”，不等于危险或放行；历史限制保留可追溯并只约束相关动作，不挡无关知识问题。否定句、无症状和无约束要结合语义处理。
3. 对真实危险信号，先呈现与风险相称的安全建议并限制可能伤害的具体训练操作；必要时建议及时专业评估。仍可在适合的范围解释问题，不因一个全局 hold 禁止全部问答或联网。不得凭模型输出解除既有安全限制、下医疗诊断或虚报放行；矛盾或证据不足要明确并追问。
4. 训练安排可由模型综合提出和修改候选，展示目标、依据、权衡、冲突、风险、变更范围及复查条件。候选的产生、讨论和个人数据读取属于授权问答；只有用户确认具体预览后，才通过现有正式计划事务做版本、范围和限制复核、幂等提交、持久回执及可撤销处理。当前实现仅首周可确认，后续扩大范围需另行实现；模型不得直写或假称已执行。
三、服务端身份、授权、快照与并发
使用真实服务端鉴权主体及服务端校验的本人 athlete 绑定，不信任客户端自报身份或 dev-user。授权采用可撤销的持久记录：主体、人物、用途、允许的资料类别、模型/检索服务类别、授权依据、说明版本、创建和撤销时间；每个请求引用该记录。授权持久化须依现有明确授权做账户迁移，不反复弹框；支持设置查看与关闭。超出所请求教练用途或涉及他人资料需单独授权。
快照与持续授权解耦：一个授权可引用多个独立、短期、请求级快照；快照完成后清理不撤销持续授权。迁移现有 UNIQUE 关系和撤销逻辑，安全迁移旧数据。绑定主体、人物、问题、用途、资料清单、来源修订、生成时点、过期、授权版本及内容哈希。资料来自客户端时标明 USER_DECLARED，校验所有权和格式不等于服务端独立证明其真实性。
将数据代次与快照 ID 分离：仅事实、授权等相关版本变化时使依赖它们的结果过期；创建另一请求不能自行更改事实代次。独立并行问题应都能完成；同一事实被修改时仅使依赖它的结果过期，无关问题继续；相关普通问答优先标注旧快照或基于新资料自动分析。身份切换或关闭时按原主体阻止旧结果作为当前。服务端调用前复核权威版本，返回/展示前再复核；未同步的离线编辑只能标明已知范围，不能谎称服务器已验证最新。对局部版本变化按依赖集失效，避免无关更新反复阻断。
明确账户绑定、迁移、快照创建/读取/清理、会话过期恢复及跨设备变更路径。正常有效会话静默续期；不能靠禁用校验解决身份失败，也不能因初始化错误让正常用户长期卡住。故障提示具体可处理原因和本地结果。
四、上下文和深度判断
建立按任务选取的版本化 CoachContext，以本人资料为限，包含来源、发生/记录时间、单位、修订、状态、证据质量及明确的未知项。区分目标、计划、已完成训练、主观反馈和模型推断。按需纳入：目标与赛期、能力和个人基线、近期及历史同协议训练、跑步分段与力量动作组次、恢复与限制、饮食及相关课表、对话中已确认信息。事实有冲突就并列，不把目标或草案当实绩，不用设备间不兼容数据制造趋势。
按任务获取足够的长短期证据，而非机械限制 14 天/6 条；长历史可先计算可溯源摘要，再按问题补充原始证据，记录覆盖时间、缺项和截断。结构化白名单、服务端大小限制、提示注入防护及用途限定保障数据使用；不靠扩大任意文本上传实现深度。优先传与问题有关的训练资料，不附带无关账户信息或精确位置。交互展示“已参考/缺失/截至何时”，允许追问引用相同会话上下文；依赖修订后重新分析。
模型需要承担综合解释、假设比较、反证、个体取舍、可执行候选及复查，不只复述规则。规则引擎负责可信计算、明确风险约束和事实版本；对输出按个人事实数字、可复算数字、一般教育示例、个体剂量、诊断/放行和写入声明分别核验，前后端共享策略版本。普通科普数字和一般因果不能因正则被整段吞掉；无来源的个人数字、确定性诊断、危险放行或虚假写入不能混同于一般解释。输出需区分事实、推断和未知，不能以“通过核验”暗示科学结论已证实。
五、模型推理与网页检索是两条能力
调用在线模型不等于搜索网页。需要最新赛事、规范或研究时，调用独立检索服务，附来源、日期、可核对链接和与问题的相关性，模型再综合；普通个体训练分析可主要依据本人记录和模型推理，不必为每题执行网页检索。给检索服务默认发送去标识化的必要查询，不把完整私人快照塞进搜索词；如确需个人细节，应符合已授权用途和服务披露。
状态分别记录模型调用与检索的未请求、成功、失败。模型可用而检索失败时明确“未能检索最新资料”，继续基于已有资料回答并限定时效；不得声称查到来源。模型不可用时明确在线分析不可用，提供标为本地规则/已有数据的有限回答，不能伪装为同等深度的模型结论；可供用户主动重试。两个服务均恢复后正常自动使用。请求已发送但结果不明时先查幂等状态及账本，不盲目自动重复付费。
六、额度与运行保障
管理员按预计正常使用量配置持久预算、周期、最大单次成本、并发和告警阈值，避免零预算、过低并发、过期账户或未运行迁移导致常态阻断；调用前原子预留、调用后结算，失败/取消/未知分别对账。使用请求幂等键和绑定哈希防重复扣费，费用保留服务端审计。真实触顶时准确说明并提供本地降级、恢复时间或管理员处理路径，不能静默突破预算或每次询问权限。预算数值和付费部署不应由此文凭空认定已获批准；实际预算、密钥、迁移、监控和部署需按照已有项目权限配置。
运行状态应显示请求阶段和真实原因：身份失效、配置缺失、快照过期、预算不足、检索故障、上游超时、输出校验失败、已发送/已返回/未知；不泄露密钥或原始敏感资料。记录匿名化指标与策略版本，分别监测普通问题成功率、误拦、耗时、空上下文、预算拒绝及重复计费；对故障报警。授权撤回/开关关闭后阻止新请求、取消在途并不展示过期结果，但已送达上游的数据和可能费用须按真实状态说明。
七、实施顺序与验收
1. 纠正路由与权限：移除逐次 consent UI，迁移持续授权和快照关系，分离危险任务与一般问题。确认当前主体启动正常、开关可关闭、撤回有效，不能伪造主体。
2. 补足上下文和模型职责：实现按任务选取、来源修订、摘要和回查；让模型生成有依据的分析与候选，规则负责约束和校验。同步服务端及前端输出策略，替换粗粒度因果与数字正则。
3. 贯通可靠服务：执行受审迁移、配置身份、账本、预算及服务；验证并发、取消和对账；接入独立检索与来源标识。先用替身端到端测试，再在有真实环境和费用授权时做小规模受控验证，不在本次设计中调用付费 API。
4. 行为验收（覆盖前后端真实路径）：普通知识、无症状、无约束、控重、一般数字与因果均无需弹窗并进入模型；已知旧疼痛仍保留限制但无关知识可回答；带痛跑或危险饮食得到相称安全处理，不得放行；个人无依据诊断/虚构事实和虚假写入均被纠正或拒绝。正常问题要求有分析与取舍，不接受固定模板仅重复数据。
5. 上下文验收：已授权且存在的 14 天之外记录、训练课表、组次、饮食和追问按问题正确纳入；不存在或不兼容的资料标未知。事实更正使依赖结论更新；目标/计划不变成实绩；跨用户信息不得进入。验证有来源的个体数字与可复算数字，教育示例不误拦。
6. 可靠性验收：有效会话下一次开启后连续多轮无二次同意；两次并行独立请求互不因创建快照失效；事实修改、登出、撤回与跨端更改使相关结果失效；快照清理不撤销持续授权。常规配置下身份、额度和快照可成功通过，不得靠关闭安全验证；超限、上游超时、重复请求及未知结算如实展示并正确对账。
7. 降级与执行验收：仅检索失败、仅模型失败、两者失败分别呈现真实来源与能力限制；未检索不得声称已查网。候选可生成但未确认前正式计划不变；确认时版本冲突要求重新预览，成功后有持久回执，撤销不覆盖后续修改。

建议复用这些对象和确认事务，形成一条可追溯链：目标及限制 → 能力与证据 → 目标时间线 → 阶段目的/条件 → 周草案 → 单课 → 实际执行与反馈 → 仅重算受影响的未来候选。每个判断或候选记录来源 ID/版本、发生与记录时间、适用任务、冲突、缺失、理由、观察点、失效条件；未确认提案不写日历，修订保留历史。先核验 S1 服务端快照与 deriveCoachBrief 的消费链，再声明聊天能使用这些信息。若依赖审计或重算失败，显示待同步/失效，不展示旧结论为最新。
分层输出
1. 短目标：明确主次目标、项目、期限、可用时间和限制；区分用户愿望、实测成绩、设备预测。输出“可评估/条件不足/目标冲突及取舍”，不保证成绩。期限过期或提前时标出并请求更新；未知赛期不伪造倒计时。
2. 长期阶段：1–52 周展示阶段目的、证据条件、关键赛事与复查点；进入/退出条件是可核验的计划规则，不冒充生理阈值。未来阶段和周均标为条件草案；不足的数据不细化为确定剂量。赛期和目标变更使受影响的未来阶段失效。
3. 周微周期：呈现关键课目的、跑力冲突、时间/器材约束、恢复机会、营养准备与可替代时段；保留已有预算口径。现行机制仅支持首周经显式确认后写入；未来周可给具体但有条件的课型、安排和复查点。未来扩大批量确认是产品能力设计：须明确确认范围、依据版本、冲突检查、数据变化失效与撤销边界，不把当前首周限制写成永久产品上限。冲突或保存失败保留原安排和失败回执。
4. 单课：分别呈现热身、主课、组/轮、组间与轮间恢复、结束及预计目的；实际与计划分开。部分完成、未知恢复、分圈和手表来源各自记录；未知不是零。每次训练的强度、完成质量与主观反应分开保存。
5. 调整与观察：复用同协议反馈分组，记录可比暴露、关联训练版本、反馈时点、独立活动、干扰、反证及缺失；按候选变更评估，而非每次重建画像。优先一次改变一个可解释变量，写明保留项、依据、复查点和撤回条件。两次门槛是现有产品策略，不是最佳剂量证据；不同强度、协议或设备不得自动推广。

二、逐项设计、依赖、异常与验收
C 运动能力与个人证据
C01 画像层次：已实现 cycle/portrait.ts及assessment/history.ts提供训练概况、可核实成绩和未知项。建议分开展示已确认表现、分项能力、近期状态、任务适用性与训练经验，不用总分替代；能力不足为未知。依赖训练事实、目标、测试协议及主体归属。验收：快速跑者可同时是力量新手；近期疲劳不变成永久能力低，朋友成绩不归本人。
C02 证据强弱与有效期：已有来源、协议和修订基础；建议对每个判断展示支持/冲突记录、日期、适用项目与撤回条件，按任务配置可审阅的新鲜度策略而非伪造统一有效期。依赖版本化事实和失效传播。验收：目标、PB、设备预测、近期实测保留类型；修正成绩后关联判断标为待重算，历史可追溯。
C03 基线与阶段：health/analysis-evidence.ts可对同来源设备协议做过去 30 天描述，少至一日也能计算。建议独立显示样本覆盖、测量条件、描述差异和阶段参照；样本不足不得称稳定正常范围，设备更换分段。验收：一日、多日和缺测显示不同证据覆盖；换设备不硬拼，持续下降不自动被吸纳成正常。
C04 响应与撤回：已有 72 小时窗、同协议分组、干扰和训练版本关联；建议保留支持与反证、事件时间、关联强度和候选解释，更正/删除训练或反馈后使依赖失效、重算并保留旧结论版本。验收：新证据可削弱旧判断；两次低强度耐受不推广到高强度；相关不表述为因果。
E 跑步单课
E01 结构和执行口径：已有结构及历史比较；建议以结构化块/轮/分段和恢复类型映射导入分圈，显式表示缺失、部分完成及匹配置信度；热身、主课和结束各自聚合。依赖训练导入与修正投影、assessment/history.ts。异常：分圈与计划无法匹配时保留原始分圈并请求确认。验收：两轮及两种恢复不被展平；缺恢复不为零；修改一圈后合计只更新一次。
E02 专项与目的：training-models/physiology.ts已有 400/800/1500 等有限模型，预测成绩仍有未知。建议先标课型、专项及目标，再用同结构同条件比较，区分训练观察、最大努力测试和设备预测；不把模型自动当配速处方。验收：同分段在匀速与递增课有不同解释；400、800、1500、长跑各自显示适用范围与缺项。
E03 波动与短板：已有可比历史和慢速加高 RPE 的复核规则；建议呈现趋势、对照条件、环境/睡眠/执行等竞争解释和下次观察条件，而非单次定性永久短板。验收：单次掉速仅触发复核；连续同条件记录可更新判断；设备或路线变化降低可比性。
E04 技术与迁移：建议把教学示意、用户提供的个人观察、测得能力、预测分别标识；没有可验证的个人动作数据不得做跑姿诊断，末段冲刺不推整场能力。依赖动作资源审核与个人观察的来源/授权。验收：通用图卡不称个人诊断；跨课型迁移仅作待验证假设。技术诊断和性能推断规则待专业审阅。
F 力量
F01 按目标选课：personal/planner.ts已有按经验、时间和器械的初始模板，该入口最多两个非相邻日，且没有读真实跑课日历联合优化；cycle/planner.ts更多复用熟悉动作。建议复用目标、器材、经验与现有课程，区分跑步辅助、增肌、最大力量、爆发与学习任务，先核查实际跑课和用户限制。验收：同动作在不同目标下给出不同选择理由和观察，不声称所有入口限制两天；缺拉类器材显示缺口。
F02 进阶、停滞和替代：现有周期支持反馈减组，未证明完整加重闭环。建议先核对同动作协议、实际完成、质量、可用器材和限制，再给可拒绝的单变量候选；停滞复核时间、恢复、记录口径与目标，不自动加重或换动作。替代保留目的及未等价之处，使用现有确认/撤销。验收：缺RIR时仍可依据已完成动作和组次给出条件性维持、重复练习或补充观察；缺关键质量或器材不编造确定加重；冲突限制阻止相关候选；拒绝保留原课，已开始课程不覆盖。具体进阶条件待专业审阅。
F03 容量与主观强度：已有组、次数/时长、重量校验；建议规范单侧/双侧、辅助重量、自重、跳跃、失败组与 RIR 的来源和单位，外部容量与主观强度分开，不推肌肉刺激或恢复百分比。验收：单侧记录和辅助重量不误乘；更正重量不重复累积；缺 RIR 保持未知。
F04 资源与教学：本交付包排除关键帧，不能断言线上 404 或动作正确。建议在完整构建产物审核资源身份、加载、动作关键帧顺序和语义，标注通用教学与个人适用性；失败时降级为文本/待核实。验收：错误重复帧被发现，资源与动作一致，缺包和在线缺失分别报告；专业教学质量由合适人员复核。
G 周期
G01 目标可行性：已有目标日期及优先级参与筛选；建议联合 C 证据、训练经历、时间、赛事和限制展示冲突、条件与取舍，不提供成绩保证。验收：同目标不同基础给不同理由；过期或提前比赛重新评估；未知能力不虚构配速。
G02 多尺度阶段：保留 1–52 周及首周确认；补阶段目的、可观察的进入/退出条件、复核点及未来条件草案标签。依赖 cycle/planner.ts 阶段和 cycle/host.ts 确认；近赛事、无赛期、过期目标单独处理。验收：8/12/24/52 周长期方向与近周详情区分；重算不改变已完成历史；按现行机制未来周不能直接写入。
G03 跑力协同：核对现有预算、真实日历和优先级，显示关键跑课与力量的目标、同日顺序/间隔信息、资源冲突及可行备选；未覆盖预赛决赛、多峰则明确需人工复核，不保证全局最优。验收：关键跑课前力量安排理由可追溯；日历空缺显示未知；冲突不会被设备状态分数自动覆盖。
G04 调整与重排：现有 planner.ts 的 index===3 会在非 TAPER 第四周力量减组并标记 focus；这是现状，不是生理规律。建议分离固定第四周“复核提醒”和有证据/用户选择的实际减组提案；将实际日期、阶段及关联反馈作为依据。漏练先查原因和原课目的，提供有限 MOVE/SWAP 或重排候选，不默认补双课；借用未开始校验、确认与撤销。验收：同一日期改 3/6/12 周窗口不无故变剂量；同剂量不同反馈第四周可有不同提案；已执行记录不被改写。
G05 长度解析：cycle/request.ts目前识别四周/一个月，八周、12周周期返回空请求，可能沿用默认或保存值。建议聊天和表单共用结构化字段：历史窗口、未来长度、赛期与是否保存目标；生成前回显解析结果，日历月有歧义则明确澄清，不静默换算或回退。验收：“未来八周”“12周”分别为 8、12；“三个月”明确解释或澄清；“近两周做后面四周”为 14 天/4 周；否定、第三人称不写计划。
H 恢复与限制
H01 一致口径：复用 health/analysis-evidence.ts 的同设备、同协议与单位过滤，统一健康页、问答、计划的 HRV 定义、来源及缺失；未知算法不得混合，相关信号不重复计票。验收：同一事实各入口口径一致，设备切换分段；普通指标正常不解除独立疼痛限制。
H02 固定规则与响应：health/recovery-assessment.ts已有近期剂量、指标、自报和肌群重复暴露；adaptive-review.ts已有个体观察。建议分别展示暴露、全身状态、局部反应、生活负担、数据质量及竞争解释，肌群图不显示真实恢复百分比。验收：低 HRV 而表现正常时保留冲突；跑后力量及其他干扰可见；相关不写因果。
H03 数据不足与许可：现有恢复评估中任何正疲劳/酸痛或恢复感非10可阻止无不良信号状态；建议拆开资料充分性、关注信号、对特定动作的约束/候选，保留明确疼痛或疾病限制。一般知识和事实回看可回答；资料不足不等于完全恢复，也不因为状态好自动增加强度。验收：未填写、恢复7和10解释不同；普通轻微疲劳或缺HRV且近期训练可用时，可给有条件的维持、替代或观察候选；正常分数不覆盖独立限制；范围明确的旧膝部限制不自动阻断无关上肢训练或知识。阈值与训练许可的专业适用性待审。
H04 症状语义：下层已有否定等处理但 R5 前置分流仍有反例；建议统一症状、否定、主体和发生时间解析供真正发送入口与下游使用，无法判定则保留歧义，不自动解除限制。验收：本人/朋友、现在/历史、疼痛/酸痛、肯定/否定均从发送入口覆盖；规则的工程测试与专业审阅分别记录。
H05 历史限制：已复现旧疼痛可继续 hold 而 14 天窗口 groups 为空。建议显示限制源、日期、关联动作、状态、复核路径与受影响任务；历史限制不因窗口外自动消失，无关知识不全局阻断，解除由对应事实和权限流程处理。验收：旧限制可追溯，影响动作仍受约束，信息问答可用；更正证据触发重新评估而非静默解禁。
I 营养
I01 食物与份量：已有餐食事实、损坏与空记录区分；建议保存来源、品牌、生熟、油量、份量、可信范围及修订；图片识别仅为待确认估算。验收：未知油量不伪精确，半份修订更新该餐及汇总一次；无法识别不伪造食物。依赖现有餐食记录与 online-nutrition-facts.ts。
I02 完整性与消耗口径：记录已记餐次与覆盖声明，区分活动热量、总消耗和估算口径；缺失不代表零。验收：仅一餐不能推全天赤字；活动热量与总消耗不重复叠加；未确认全天完整时不做确定性判断。
I03 持续反馈：personal/planner.ts已提供维护量、目标区间和蛋白起点，但本反馈入口不依据体重趋势调整热量。建议分控重、增肌和训练补给路径；定量估算需检查称重及餐食覆盖，数据不足时仍可根据已知课表、时间、预算和饮食限制给有条件的定性餐食选项；结合训练变化、时间与就餐条件触发复核；显示公式估算、实测趋势及可拒绝的修订，不自动修改。验收：漏餐不判摄入不足；两段完整趋势可触发复核而非机械调量；预算或目标变化影响建议，拒绝保留原目标。具体能量、营养剂量和特殊人群规则待专业审阅。
I04 身体、训练与营养联动：复用有效画像、实际训练和餐食事实；目标、已确认课程、取消训练、体重修正或饮食限制变化使相关提案失效并重新评估。验收：目标体重不覆盖实测体重；取消训练后对应补给提案说明更新原因；同步失败时旧提案标记待刷新。

1. 证据与安全依赖先行：核对真实发送路径、S1 快照、主体/日期与症状解析，统一限制状态、版本和失效传播（C、H）；检查 src/lib/health/、src/lib/coach/assessment/ 与现有更正投影，避免复制指标源。明确只读知识与受限制训练建议的权限差异。
2. 请求与周期闭环：扩展 cycle/request.ts 并在聊天与表单共享请求；沿 cycle/host.ts 保留首周确认、过期/冲突检查、回执和撤销；planner.ts拆分第四周复核与有依据的变更；复用 r4/course-flow.ts，先验证已有预算和边界。
3. 课型与跨域联动：在既有结构化训练、cycle/portrait.ts、personal/planner.ts 和营养事实桥补目的、口径、比较条件与失效关系。动作资源需完整构建产物，不因交付包缺文件判断线上故障。
4. 验收分层：对解析、版本、计算和幂等用离线确定性测试；从用户真正入口做合成端到端测试；另设专业审阅对照，验证规则合理性及适用边界。复用 cycle/{adaptive,adaptive-import,cycle,host,review-findings}.test.ts、assessment/history.test.ts、health/recovery-quantitative.test.ts、个人响应与 personal/personal.test.ts，先核实文件存在和命令；本方案未执行这些测试。

8 2 每项任务的工作步骤
1. 按本方案和现有源码定位当前行为，先用合成输入复现原问题及相邻正常场景。
2. 明确该任务复用的数据、输入输出、依赖版本和失败状态；保护当前记录、有效限制及已批准计划。
3. 先编写行为测试，确认旧实现触发预期失败；再做最小增量修改，并运行针对性测试。
4. 运行受影响的组合场景、失败注入与回退；涉及界面时验证真实入口而非仅内部函数。
5. 独立复核数据一致性、普通问题体验、风险对照和跨域调用；记录通过、失败和仍待核项。
6. 必要时进行对应专业审查与真实环境验证；只有具体版本、环境和证据相符才标完成。
8 3 首批必须保留的验证与反例
存储：IDB失败且localStorage配额失败；慢写；意图写后关闭；目标已写但回执未写；回退失败；日志不可读；镜像延迟；跨标签旧版本不配合；大键与总量超旧阈值的完整往返。
对话：没有腿疼、不是没有腿疼、没有胸痛但腿正在疼、朋友腿疼、旧疼痛加当前无痛与知识问题、控制体重及明确危险行为、未知资料与有效限制；不应互相套用。
校验：通用教育数字与个人事实数字、有效引文与错误单位、一般因果与个人确诊、没有修改与声称已经修改；两端按同一策略分类。
训练：400/800/1500/3000/5000/10000米六项及其他长跑不同目标；同一成绩不同经验；8/12/24/52周；阶段切换、比赛提前、漏练、器械不足、跑力冲突和明确限制；首周与未来周权限不同。
营养恢复：未知餐次、份量纠正、目标变化、缺睡眠、设备更换、正常HRV与疼痛并存、可比与不可比反馈；数据变更后旧提案不再显示为当前。
回归与环境：保留当前hydration失败基线，分别记录类型检查、前端构建、模块和集成测试；Cloudflare Functions、真实服务、iPhone/iPad Safari、品牌账号及数据恢复演练按环境单列。
九 整体完成的定义与待确认事项

附录 复核结论
上一版方案经数据工程与教练能力两路独立复核；本版针对联网常开另行复核，明确正常问题自动联网、模型承担深度判断、历史上下文补足、用户不逐轮确认以及快照并发隔离；已进一步区分自动更新建议与确认正式写入、局部澄清与整个问题拦截、资料变化后的局部失效与无关问题继续联网。复核指出：旧版本标签可能绕过恢复锁；权威值与镜像应按物理位置分别回退；日志或版本分裂不能被当作成功；D03和D04必须纳入阶段；已有默认联网与避免重复说明的历史偏好不能降格为未知；六类跑步项目需要独立验收。以上已纳入正文，并补充跨域快照、授权状态、规则台账与连续任务案例。复查发现提交结果不确定时回滚和重启策略可能冲突，已明确可证实的COMMITTED为不可逆提交点，并加入提交回执读回失败、提交后缓存失败和再次崩溃的对照测试。
复核未证明程序已实现，也未证明真实环境或专项处方已经通过；其余条件按各章节验收。
