# 补充：桌宠饮食输入框、本地食物库与联网查询

本节根据用户最新要求调整此前桌宠方案：**饮食以弹出输入框为主，结合 App 本地食物库和联网查询快速登记**；桌宠分身未来可能放到设备桌面。这里是设计方案，不表示外部桌面小组件或联网食物查询已实现。

## 1. 用户要的体验

轻点方坤桌宠 → 点“记饮食” → 弹出输入框 → 输入食物/品牌/份量 → 直接显示本地库和联网查询结果 → 选择/调整 → 点一次“保存”。该按钮本身即对当前预览的确认，不重复弹同样的确认框；继续记一项或完成后回到原页面。

例：输入“鸡胸肉 150 克”，先显示本地匹配并同时尝试联网查询；明确标出来源、品牌或食物类型、生熟口径、每100克/每份及营养成分。用户确认正确条目和份量后，一次保存。输入“米饭和鸡蛋”可拆分为两项，未说明份量的项目保持待补或未知，不能自动假定重量和精确热量。

用户也可直接手动记录，或选常吃/最近记录并调整；查不到、离线、网络错误时本地库和手动输入继续可用，不因网络问题拦截记录。

## 2. 本地库和联网查询怎么协作

1. **本地优先展示，联网自动补充**：随输入先即时检索现有食物库，再在联网启用且服务可用时查询在线来源，无需为每次检索逐次确认。使用防抖、取消过期请求和必要缓存，不能用过期查询结果替换当前输入。
2. **来源分开、信息可信**：候选分别标“本地库 / 联网来源 / 用户自填”，写明品牌、地区、品名、生熟、规格与单位；联网结果带来源和获取时间。不同食物或不同包装不能因为名字相似自动合并。未经真实检索不得编造“已联网查询”或来源。
3. **单位与份量清晰**：每100 g、每份、克/毫升/个/碗等保留口径；缺少每份重量时不能凭空换算克数。营养数字来源不全要标缺失，不能将未知算成0；允许用户修改份量、品牌、生熟和每份规格。
4. **优先使用最少必要信息**：普通食物查询只需食物名、品牌、地区等；不默认上传体重、训练记录或用户身份。保存时记录用户、日期、餐次、食物条目、份量、来源、估算与修订。用户要方坤分析全天饮食时再按问题提供相关事实。
5. **失败与成本**：如在线接口、网络或额度不可用，直接显示“联网查询暂不可用，本地和手动输入仍可使用”。真实提供商、数据授权、价格及地区覆盖待选型和验证；没有真实调用不能声称联网营养查询已存在或数据准确。

## 3. 界面细节

- 桌宠菜单中的“记饮食”打开输入框，支持键盘快速输入和选择食物；右侧或下方直接列本地/联网候选，不要求进入多层页面。输入、候选和草稿在手机键盘出现时仍可操作。
- 先选日期/餐次，支持自动识别“今天午饭”并允许更改；“昨天晚上”须按本地日期处理，不默默写今天。餐次或日期无法确定时允许核对。
- 结果选择后显示食物名称、份量、生熟、能量与营养已知项及来源；多食物可继续添加，统一一次保存。明显不确定的热量展示“未知/估算”，不伪造精确数。
- 保存后显示明确回执，并可继续记、查看或有条件撤销；用户再次提交同一草稿不重复记。保存失败保留草稿并支持重试，不把查询成功当成登记成功。
- 后续问“这顿怎么样”，方坤调用实际已保存或明确标为草稿的餐食；如果全天不完整，只谈已记录部分，不断言全天赤字。

## 4. 未来设备桌面：预留但不假装已经支持

当前桌宠是 App **内部**悬浮组件，不是系统桌面宠物。用户希望将来可能放到桌面，方案需把“桌宠展示”“快捷输入”和“记录/搜索服务”分离，使不同入口复用同一数据与权限，而不是把业务逻辑写死在 App 页面。

桌面入口可以考虑：系统小组件、快捷指令/深链接进入 App 的登记面板，或在平台允许时使用独立悬浮界面。**不同操作系统限制不同**；iOS/iPadOS 主屏小组件的交互、后台运行和覆盖其他 App 等能力必须按目标系统及版本实际核验，不能假设一个 App 内悬浮窗能原样放到系统桌面。Android、桌面电脑等也需分别验证。

建议先完成 App 内输入框和统一记录接口；未来外部入口优先打开同一登记流程，复用当前人物身份、草稿、网络状态及保存回执。系统小组件若不能完整输入，则提供快捷按钮跳转；不能用不可靠后台写入来冒充保存成功。设备锁屏和外部桌面入口应避免无意展示隐私信息，权限和登录失效要有可理解的恢复方式。

## 5. 当前源码事实与后续任务

现有 `src/lib/nutrition/lookup.ts`、`food-db.ts` 提供本地搜索；`src/components/fangkun-ui/nutrition-panel.tsx` 有搜索食物和手动录入，界面说明数据包并非本轮联网核验。桌宠当前点击仅显示固定气泡。未发现即可用于桌宠输入框的真实联网食物查询闭环，需继续核实接入，而不是宣称已实现。

### 可交给实施者的验收

- 输入同名不同品牌、地域、生熟、份/100g结果；本地结果和联网结果各自显示来源，未知份量不变0；快速切换关键词、断网、超时、旧响应回到当前列表不发生错配。
- 输入多项和跨餐时间，编辑、一次保存、重复点击、刷新后核对、撤销冲突；确保同一人物且不重复记餐。
- 线上来源过期或错误、缺营养字段、服务无权限、费用未配置时，保留本地查询和手动登记；不显示虚假来源或虚构精确值。
- 桌宠拖动与输入、键盘遮挡、安全区、关桌宠后的替代入口、方坤页隐藏桌宠下同等功能；在桌面外入口尚未实际实现前，不写“已支持系统桌面”。
- 真实服务、目标平台和适当授权后再测试数据覆盖、性能与费用；本轮无产品代码或真实联网查询修改。

# 方坤桌宠分身：快捷登记与反馈方案

## 1. 定位

桌宠是方坤在 App 各页面的随身分身。用户不用先切到多个模块，点击桌宠就能说一句话或选择快捷卡，完成饮食、训练反馈和身体状态登记，并可随时让方坤分析；完整数据与长期判断仍使用 App 现有的同一套记录和教练能力。

这里的桌宠是方坤 App 里的 `FloatingPet`，不是 ChatGPT 宠物。当前源码桌宠点击为固定提示、可拖动、长按收起，记录后会播放状态；不承担登记或数据写入，在方坤页隐藏。下文是拟议能力，尚未实现。

## 2. 用户使用路径

### 2.1 最常用路径：点一下、说/填、保存

1. 在任意支持页面点桌宠，打开轻量面板；首屏直接有输入框和三个常用快捷项：**记饮食、补训练反馈、记身体状态**，另有“问方坤/更多”。用户可调整排序，避免固定一个入口适用于所有人。
2. 用户输入一句话，如“午饭吃了两碗米饭和一份鸡胸肉”“今天跑完RPE 5，左小腿有点酸”“卧推30公斤3组8次”；桌宠理解为一个或多个**待保存草稿**。
3. 草稿卡直接显示识别到的对象、时间、份量/数值、来源和未知项，可点字段改；缺的非关键项可以空着。用户点一次“保存记录”，这一次动作就是对卡片所示内容的确认，不再弹一遍重复确认。
4. 成功后反馈“已记录”，提供查看、继续记录与可条件撤销；失败则保留草稿和原因，不播“完成”或重复写入。要分析时点“让方坤看看”，可沿用当前记录和对话。

桌宠是一个更短的入口；用户依然可以在相应页面记录，关闭桌宠不影响功能。用于查看和提问的操作直接进行；改动已保存的正式计划或历史记录时仍展示前后差异，再由用户确认。

### 2.2 饮食快捷登记

- 文字：`午饭米饭两碗、鸡胸肉一份` → 分成食物项目，标记份量口径待确认；不知道克数和做法时保持未知或明确估算范围，不编造热量。
- 照片：用户主动选图或拍照，显示待核对识别结果，可增删食物、改份量、确认餐次。**拍照记录、图片识别与上传不是同一件事**；权限、可用服务及费用状态清楚告知，识别失败可直接文字登记。
- 常吃餐：用户从本人已保存餐食或收藏选择，默认显示份量供编辑；日期和餐次取当前界面但可改。常用模板仅基于该用户，不自动创建不存在的食物。
- 同一句“早饭鸡蛋两个，午饭牛肉面一碗”拆成两餐两项，时间不明则询问或保留未确认；保存前统一显示，避免跨餐混写。一天只记一餐时不称当天总摄入或能量缺口。

### 2.3 训练与手表反馈

- 用户在一节训练详情页点桌宠：优先带入该页面明确活动身份和日期，显示“正在补充：跑步 A / 6.01 km / 日期 / 来源”，可更换；只附加感受，不新建第二条跑步，也不覆盖手表原始数据。
- 一句“这节 RPE 7，左小腿酸 3 分，无疼痛”分别解析整课 RPE、酸痛、部位和明确无疼痛；遗漏为未知。明确哪个训练、量表和时间；跑步与力量组合课的整课 RPE 不能自动分配给两个分项。
- 若同天多节课、跨页面或没有明确训练，列出候选并只问“哪一节”；用户可跳过关联，将独立反馈作为独立记录，不自动归错课。
- 力量可写“深蹲40公斤3组8次，组间2分钟”，预览动作、单手/总重口径、组次与休息；已有重复组可复制再编辑，未做和未填分开。
- 手表同步完可给一条轻提示“新活动待查看”，用户选择补反馈或问方坤；不得把手表心率、体能评分当成用户主观感受，也不能假设同步/后台已可用。

### 2.4 身体与健康状态

体重、睡眠、自我感觉、酸痛及疼痛分别登记；输入“昨天睡6小时，今天疲劳6分”时保留各自时间及量表。仅在用户明确说出“无疼痛”时作为本次无疼痛自报；无记录不是零，不自动清除既有伤病限制。用户提到明显严重或急性危险信号时，桌宠先显示即时安全提示，再允许处理无关问题，不自行诊断。

## 3. 桌宠怎么理解用户

1. 文字优先支持简短自然话、日期、多个动作/餐次、单位和顺序变体；已知 parser 存在“深蹲40公斤3组8次”重量丢失、“26分52秒”时长未识别，先修复再扩展。
2. 在设备支持并经过用户授权时，可用语音转文字，先展示识别结果，允许修改后再保存；转录失败、环境嘈杂、网络缺失或无权限时，文字与卡片仍可用。明确语音是在本地还是传给服务处理；不能假定 iPhone 的各浏览器都有同样能力。
3. 用户可以混合输入“记下晚饭，再分析明天训练”。登记与分析分为两个明确任务；草稿未保存时分析可注明依据为待确认输入；用户保存后关联正式记录；计划的修改另走预览确认，不静默写日程。
4. 已有资料可复用，但不能因曾经吃某种餐、曾用某个重量，就自动把它当本次实际值。用户本人、朋友、示例和否定说法分开；明确日期可回填历史，不能一律记今天。
5. 处理超长文字或语音时，应显示哪些片段未识别、未发送或需补充；重要条件不能截断后当作完整信息。

## 4. 数据、确认和撤销

- 桌宠所有输入先进入与现有训练/饮食/健康入口共用的草稿和验证流程；保存通过对应模块的统一写入服务，不能另建一套桌宠数据库或绕过用户/人物隔离。
- 正式新增记录：清晰预览后**一次保存**，这是用户确认；照片识别、未知单位、可能重复活动在同一预览中说明。常用输入可以减少字段与步骤，但不猜造未说出的内容。
- 更正、删除、关联手表和修改正式计划：显示目标、前后差异和影响后确认；写入使用版本检查和幂等键，重复点击只记一次。冲突提示重新核对，不覆盖后续记录。
- 成功必须等持久化回执；未完成/失败时保留草稿，提供重试。撤销只撤销本次操作，若后来已有修改或已执行训练，则告知冲突并重新预览；训练历史和手表原始资料保留。
- 保存或更正后让训练日志、餐食汇总、健康状态、教练画像和相关草案依据同一事实更新；自动联网服务的开关依旧遵循用户已确定的常开方向。打开快捷面板不等于自动上传所有个人资料。

## 5. 桌宠交互设计

- **轻点**展开/收起快捷面板；**拖动**保留移动；当前长按收起和位置记忆作为既有交互保留，面板另提供明显的“关闭桌宠”和设置入口，避免用户误触后找不到恢复方式。
- 面板跟随屏幕边缘自适应，避免遮挡训练记录、底部导航和手机键盘；输入与预览在较小屏幕可滚动，完成后不跳离用户原页面。桌宠不因动画遮挡或打断输入。
- 支持触屏、键盘、屏幕阅读器，按钮有明确文字和较大触摸区域；减少动效/隐藏桌宠时依然可用其他入口。
- 与方坤页一致：因为当前该页隐藏悬浮桌宠，方坤输入区也需要同样的“记饮食/反馈/状态”入口，并共用草稿和写入流程；不要强制在聊天里多显示一个宠物。
- 桌宠情绪与动作可以反馈“整理中/待确认/成功/失败”，同时配文字；仅当真实回执成功才做成功反馈。公共场景默认不直接在浮窗展示敏感身体数据。

## 6. 手表同步与桌宠联动

1. 连接并同步：显示每个品牌的实际连接和最近成功时间；同账号同活动 ID 幂等处理，跨品牌相似记录只提示核对。
2. 数据落地：保留设备来源、原始字段、单位、分圈及版本；无字段是缺失，不由桌宠补造。
3. 桌宠提示：只提示已确认读取或需要处理的状态；可关掉、不频繁打扰。设备权限、后台同步和 iOS 通知能力按实际支持显示，不能承诺系统后台自动完成。
4. 用户补感受：明确绑定活动，展示预览；保存后把反馈与该训练关联，避免把跑步与力量的整课负荷重复计算。
5. 方坤复盘：小型要点包携带当前选中训练及关键计算、感受、相关限制、缺项和反证；长分圈按需展开，不以截断换取错误结论。更正数据后相关分析待重审。

### 端到端验收示例

手表同步跑 A（同日有 B）→用户点 A 的桌宠“补反馈”→输入“RPE 5，左小腿酸3分”→确认卡显示 A、日期和缺项→一次保存→记录页与方坤共享同一事实→问“明天怎么安排”→结合现有计划、恢复、实际训练提出条件候选→如要改计划先预览并确认→事后更正 A 的分圈使相关答案待重审。补充断网、重复点击、返回页面、错误识别、跨人切换和撤销冲突；用合成数据先跑，真实设备及模型另行验证。

不预先承诺“只需几秒”“节省多少次点击”；比较当前入口与新入口的实际完成步骤、错误率和时间后报告。此方案未实施、未部署，也未调用付费服务。

# 手表同步、快捷登记与桌宠协作方案

基于 9263254 增量合入的独立源码副本；本节是问题盘点和拟议方案，不代表已实施或已在真实设备验证。目标是让手表提供客观记录、手动补充运动员感受和缺项、方坤统筹解释；用户选择的正式记录修改应简单清楚且可撤销。

## 一、源码现状与发现

### 1.1 手表同步已有入口，数据处理并未全部贯通

- 已有佳明同步、高驰 MCP/授权和平台状态、活动/健康数据解析、文件/截图导入及确认入口；品牌支持和字段取决于实际接口、账号授权、设备与环境。Strava 现有能力探测不代表已同步活动。Apple 健康/Health Connect 依赖相应原生能力，不应把网页当原生授权。
- `platform-sync-runtime.ts` 校验账号、数据来源和字段；设备导入页面已有预览/确认。已有确认不代表自动拿到所有分圈、力量组次，不能把手表计算分数当客观生理事实。
- 旧版训练页出现手表26:51与汇总约53:43，9263254 对明确同一活动重复时长有代码修复和合成测试；用户设备上是否修好尚未验证。
- 当用户问“去年”时，已复现上下文选择更偏近期，旧资料仍可能被裁掉；当前压缩后可能丢关键信息（前文已列）。同步成功不等于该数据被方坤实际读取或用于回答。

### 1.2 桌宠目前是展示，不是记录工具

`src/components/pet/floating-pet.tsx` 当前悬浮桌宠点击轮流显示本地提示、拖动移动、长按收起；监听记录保存后做动画，但不读取或写训练数据，在方坤页隐藏。以下快捷入口为**新设计**。不要误把 ChatGPT 的宠物插件当成本 App 里的方坤桌宠。

### 1.3 “记一笔”有基础，但常用表达会误识别

本轮对 `src/lib/ui/quick-log.ts` 的 `parseQuickLog` 使用合成输入实际调用：

| 输入 | 实际解析 | 风险 |
| --- | --- | --- |
| `深蹲3组8次 40公斤` | 组数3、次数8、重量40 kg | 正确识别这一形式。 |
| `深蹲40公斤3组8次` | 动作名“深蹲40公斤”、重量未知 | 重量混入名称。 |
| `今天跑6.01公里26分52秒` | 距离6.01公里，时长未知 | 分秒格式没有识别。 |
| `跑了6公里均速4分28` | 距离6公里，配速未知 | “均速”表达没有识别。 |
| `昨天力量卧推30公斤做了3组8次` | 日期和重量混进动作名，重量未知 | 易产生错误草稿。 |

这是**解析函数级测试**，不能直接断言用户实际保存过错误记录；正式入口已有核对步骤。下一步在 UI 输入→预览→确认→重启读取完整链路重放。

## 二、手表数据：从同步到真正可用

### 2.1 处理流程

1. **连接与读取**：按品牌显示连接、授权项目、设备/账号、最近同步时间、进度和失败原因；获取到的实际字段及未获权限的字段分别列出。账号切换时核验人物，不把别人的数据混入本人。
2. **原始记录保留**：每次活动保留稳定来源 ID、设备、账号归属、时区、发生时间和同步时间、原始字段及更新版本；不把日级睡眠或恢复评分伪造为即时测量。
3. **规范化与质量**：统一单位但保存原始口径；明确计时/总时长/运动时长、距离、配速、平均/最高心率、分圈与休息、步频、功率、负荷、睡眠和 HRV 的来源及是否可比。未获取不记 0；型号/算法变化要分段；估算值不说成实测或诊断。
4. **幂等与关联**：同账号同活动 ID 的重复同步只更新同一来源版本；同一运动的手机/手表记录先用用户确认的身份关系去重；跨品牌疑似重复单独提出，不能因同日和距离相近自动合并不同课。训练计划与手表活动保留“计划→实际”的关系，不把计划当完成。
5. **质量检查与异常处理**：显示同步新数据、已更新、重复、待核对、缺失和失败的数量；分圈缺失、冲突或身份不明时保留可用部分，用户可以稍后处理。数据核对不等于每次重复审批同源已确认记录。
6. **交给方坤**：按本问优先选对应训练与其实际分圈、心率和时间，连同目标、关键计算、必要历史和反证生成紧凑要点；超预算列明缺项，不因安全摘要压掉重要反证；用户可展开“本次用到的数据”。记录被修正/撤回后，依赖的判断和计划草案重算或标待复核。

### 2.2 哪些数据应自动流转，哪些需要核对

| 情况 | 建议处理 |
| --- | --- |
| 同一账号、同一活动 ID、已验证匹配的重复同步 | 幂等更新或无变化，给同步回执，不让用户一条条重复确认。 |
| 首次读取到活动或健康指标 | 显示来源、时间和关键字段，沿用现有导入授权及确认规则；是否可按来源设置批量确认待结合真实权限和业务入口设计。 |
| 跨品牌可能是同一课、计划关联有多个候选 | 给对照卡，由用户选；不凭相似度自动合并。 |
| 距离/时长/心率不一致或测量口径不清 | 展开各来源与差异；不把分歧两份相加，不强行指定某来源必定正确。 |
| 已关联活动后用户更正或解除关联 | 保留原始设备记录、用户修订及版本，更新关联事实；依赖的旧判断需要复核。 |
| 手表尚未同步、缺分圈或不同设备 | 可分析已有部分，注明范围；不伪造缺失数据或将空白视为0。 |

## 三、手动登记：最快输入，最少必要确认

### 3.1 三种互补入口

- **一句话**：在方坤输入“今天轻松跑6.01公里，26分52秒，RPE 4，右小腿酸2分”；解析成可编辑卡片，正确识别日期、单位、分秒、训练身份和主体。按当前设计，正式写入展示一次清晰确认，不让用户每字段重复确认。
- **快捷卡片**：最常用的训练反馈、力量逐组、体重、饮食、睡眠与疼痛；预填确定的上下文（今天或用户选中的课），未知保持空。历史或模糊日期不自动写今天；RPE可跳过而不是用默认值。
- **图片/语音**：截图、食物照片生成待核对草稿；语音转文字后显示识别文本供修改。既有照片本地保存、联网识别是独立功能；能否语音、识别服务、iOS浏览器权限及费用都需实际实现和验证，不能承诺所有设备可用。无麦克风/权限或无服务时文字和快捷卡始终可用。

### 3.2 常见登记流程

1. 已同步跑步后补充主观反馈：先选中这节课，快速录 RPE、酸痛/疼痛、备注及时间；不重复新建跑步或覆盖手表原值。无值就是未填写，不表示无痛。
2. 力量登记：选择动作或一句话；逐组支持单侧/双侧、每手/总重、次数、RIR/RPE及休息；若连续多组相同可“一键复制上一组”，明确实际完成/跳过/未填。
3. 一餐登记：常吃食物或照片草稿→份量/生熟/油量核对→保存；没有记录整天不推断全天总摄入。支持复制常用餐但日期、份量需可编辑。
4. 体重和状态：可填数值、时间和可选测量条件；更正历史日期不覆盖今天，不把目标体重当实测。
5. 保存结果显示“已保存 / 草稿 / 未能保存”，允许查看和条件撤销；可供跨页同步，保存失败不显示完成。重复提交使用幂等键，避免重复记课。

### 3.3 输入容错和错误预防

支持数值顺序变化、中英文单位、中文数字、mm:ss与分秒、上午/下午、昨天/具体日期、多动作及多条反馈；识别不到就明确保留原句、标待补充，不以 0 填充、不将重量塞入动作名称。模型提取可作为辅助，但字段需验证、可修改，并记录哪些是用户原文、识别估计、已确认数据。针对相同语义不同说法及否定/第三人/日期歧义做真实入口测试。

## 四、桌宠怎么做才方便

### 建议：桌宠是“快捷入口”，方坤是决策中控

在悬浮桌宠上增加一个轻量快捷菜单，优先复用原有教练、记录和导入入口，而不是让桌宠自己持有第二套数据或静默修改。桌宠可以按用户所在页面提供少量相关快捷项：

| 快捷项 | 点击后做什么 | 是否写记录 |
| --- | --- | --- |
| 问方坤 | 打开对话并带上当前页面/已选训练的可见上下文 | 只导航和提问。 |
| 补这节反馈 | 选中当前训练，打开 RPE、感受和疼痛卡 | 展示确认后才保存。 |
| 记一笔 | 弹出一句话/快捷卡，入口可切换训练、饮食、体重和状态 | 可编辑草稿，确认后保存。 |
| 同步状态 | 显示上次成功时间、同步进度和待核对数量；需要时进入相应品牌同步 | 展示信息或由用户触发同步，写入沿用同步规则。 |
| 查看今日 | 显示今日计划及当前待处理事项，点卡片进入对应页面 | 只读。 |

**交互建议：** 轻点打开菜单，拖动仍移动位置；当前长按是收起，实施时保留或明确提供收起按钮，不靠隐藏手势发现功能。菜单靠近桌宠但自动避开键盘、底部导航、重要按钮和屏幕边缘；支持关闭、移动、减少动效和无障碍标签。方坤页桌宠目前隐藏，教练页应直接提供同等快捷入口，不能因桌宠隐藏而无法记录。桌宠关闭时其他入口保持完整。

**节制提醒：** 同步失败或用户选择接收的待处理事项可显示小红点/轻提示；不自动频繁打扰，不在锁屏或公共界面显示敏感身体信息。自动提示应有关闭/频率设置，是否能后台通知以设备能力和授权为准。桌宠不说“已经保存”直到持久保存成功，不声称知道未读取的健康数据。

### 其他方案比较

- **只改现有各模块页面**：实现较少、页面上下文清楚，但切换页面仍费事。
- **桌宠直接集成复杂表单与数据写入**：看似一步到位，但易遮挡页面、重复业务逻辑和产生错误写入，不建议。
- **推荐的桌宠快捷入口＋方坤中控**：保留原有功能和数据合同，同时让用户在多数页面一两步打开登记或问答；需要额外做好手机触控、状态同步和误触测试。

## 五、建议实施顺序与验收

1. **先修准确性**：修复快速解析中重量顺序、分秒、均速、日期与多动作；确认前可编辑，实测正常、错误、否定、朋友、重复提交、重启后持久化。
2. **手表数据链路**：用两个虚构品牌和同一天两节课测试账号/人物归属、重复同步、明确关联与取消、分圈修正、单位冲突；用户所选训练从记录→方坤上下文→回答全程一致。先用合成数据及假服务，真实授权设备另验。
3. **桌宠快捷菜单**：保留拖动和收起，接入问方坤、补本课反馈、记一笔、同步状态；按页面预填但可撤销，可关闭桌宠且保留原页面入口。手机与桌面测点击、拖动、键盘遮挡、读屏和误触。
4. **图像/语音与个性化**：在可用设备/服务和授权明确后接入；识别为草稿，明确本地/联网状态和失败方式。不要因为此项未接入阻塞文字和卡片。
5. **观察效率**：记录新用户常见任务从入口到预览和保存的步骤数、完成率、错误率、撤销、时长；对照原入口，定性与量化分别报告，不预先承诺百分比提升。

重点端到端样例：手表同步 A→确认其来源→补充 RPE/局部感受→问“这节和下周课怎么配合”→方坤显示所用数据与条件候选→如需改计划则预览确认→修正一次分圈→相关结论待重算；同日 B 保持独立。正式恢复、真实设备、真机 Safari、服务与专业有效性仍单独验证。

# 继续完善：低成本教练分析交接的可执行设计

本节细化前面的方向。当前是设计与源码复核，未修改软件；实际收益和训练效果必须测试后报告。

## 一、先解决用户真正要得到的结果

用户问“昨天跑完今天状态怎样、明天力量怎么安排”，方坤应先给当前能确认的结论、关键依据和一个可执行方向，再允许展开数据与取舍。数据缺一部分时给有条件的回答，只补最影响决定的一项；明确疼痛或其他限制按受影响的动作保留。用户要求写进正式日程时，生成前后对照并确认。

**关键原则：App 计算和记录为基础，模型负责理解与解释，程序负责事实和操作的最终校验。** 不能为了更短提示而把真实数据、个人目标、风险、反证或缺项省掉；也不能因为不能证明所有健康数据齐全就拒绝普通问题。

## 二、在现有源码上分工，不重做整套系统

| 模块 | 现状与限制 | 拟改动 |
| --- | --- | --- |
| `online-context.ts` | 根据字词筛选事实；历史年份未按自然语言优先，32条和4800字节引用预算可能丢失关联。 | 增加任务和时间范围解析、按问题召回、重要依据与反证的完整性清单、预算排序。 |
| `online-handoff.ts` | 本地结果可传递，但字段截断至256字符，计算条件及对话末尾可能丢失。 | 改成字段级结构化数据与分段；关键字段不能无标记截断。 |
| `online-contract.ts` / `coach-declarations.ts` | 当前 V2 严格校验字段、最多32条，每字段字符串最多256字符；不能只改前端长度。 | 设计共享的 V3 契约并让浏览器与服务端同步支持；旧请求保持已有处理，新路径明确版本与拒绝原因。 |
| `coach-snapshot-store.server.ts` | 已有主体、快照、版本及授权机制。 | 在授权快照中绑定短引用映射、来源版本和覆盖清单；保留用户隔离、并发及撤销边界，不将客户端数据冒充独立验真。 |
| `coach-chat.controller.js` / `assertion-policy.ts` | 现代路径要求个人数值引用完整原文，正文中可能含冗长机器格式；条件不满足可能被拒或截掉。 | 在版本化新协议中让模型返回结构化断言和短 ID；服务端解析并校验每个数字、单位、来源版本，生成简短可读说明；维持危险行为、越权、错误来源拦截。 |
| `coach-sheet.tsx` / `coach-answer-view.tsx` | 已有 UI 卡片和部分请求逻辑，比较路径可能提前返回，长答案曾出现格式问题。 | 支持多意图逐项状态、简短答案与可展开依据，保留已选训练/日期及正确滚动。 |

上面路径基于当前 9263254 交接副本；实施时需复核最新代码。V3、短 ID 与时间窗口是**拟议方案**，不是现有能力。

## 三、面向每次问题的数据合同

### 3.1 输入和计算

每次请求确定 `athlete`、`question`、`asOf`、所选训练、分析时间范围和近期对话；本机计算仅使用相同用户且在 asOf 前可知的真实事实。动作、训练、测量、目标、预测、计划和对话是不同类型；对未确认事实保留来源与状态。

计算输出应包含：指标名称、数值或未知、单位、来源引用、计算口径/版本、时间及数据质量。HRV/睡眠等参考还要保留有效天数、时间区间、设备与协议；只给窗口中位数不能表示已验证的正常值。运动强度及恢复结论需保留支持证据与反例。

### 3.2 紧凑要点包（示意，不是现有代码）

```json
{
  "v": 3,
  "task": {"question": "这节之后明天怎样安排？", "activity": "F1", "period": "近期"},
  "facts": [{"id": "F1", "kind": "actual_run", "value": "已选跑步摘要", "source_version": "本次短版本"}],
  "derived": [{"id": "C1", "metric": "可比变化", "inputs": ["F1"], "value": null, "unit": null, "status": "unknown"}],
  "judgments": [{"id": "J1", "status": "possible", "support": ["F1"], "counter": [], "missing": ["睡眠"]}],
  "constraints": [],
  "coverage": {"omitted_categories": [], "truncated_fields": []},
  "authority": {"model_write": false, "user_confirmation_required": true}
}
```

实际字段名、最大长度和历史兼容方式由实施者与现有类型协商确定。短 ID 必须由服务端快照映射至所属人物、来源、版本和单位；模型不能自行选择新的身份或产生来源。引用一项计算至少能查到原始输入、公式版本、单位及有效时间。

### 3.3 依据如何省 token 又能核对

- 每个请求中，ID 映射仅保存一份；模型返回 `{claim, refs}`，不必在回答正文重复整段原始机器字符串。服务端从本次快照还原并验证数值/单位、事实类型和版本，不能让模型自行声明“已核验”。
- 完整原始数据留在 App 或获授权的快照中；用户点“查看依据”可看到该结论所用的来源和计算。未经允许或超出当前问题范围的数据不发送。
- 对多段训练保留总量与重要段、休息和异常；若只展示摘要，明确没覆盖多少，并能获取本问所需原始分圈。比较两课时各自证据和时间不能互换。
- 结构化列出支持、反证、限制和缺失；如果关键支持或反证缺少，就在结果状态标“依据不完整”，不能声称已完整复核。超过长度按句/字段分片并提供截断计数，不能截掉尾部还标完整。
- 客户端提交的事实、计算及限制仍是申报；服务端可以验证格式、归属、版本、可复算性及自身来源，但不能将无法独立核验的设备记录宣传为已核验。

## 四、缺资料和混合问题时怎样回答

1. 一般知识：直接回答，个人背景不必要时不发送。
2. 个人问题：能确认多少就回答多少；例如可描述一节跑的配速和心率，但无个人基线时，强度解释只能是条件性，不编造准确疲劳度。
3. 遇到无关数据缺失：不阻断本问；影响结论的关键缺项单独展示，并优先从已有记录补充，确需用户提供时只问最重要的一项。
4. 请求比较＋改课：比较结果和改课候选分别处理、分别显示状态；能比较就先给比较，必要时为改课澄清；确认前不得声称已写入。
5. 服务失败：说明是网络、配置、认证、预算、超时还是校验失败；能提供的本地计算或记录先保留。不能把本地结果伪装成模型回答，也不能把预算限制解释成用户的问题违规。
6. 跑步/力量/饮食等资料被更正时，只重新核对受影响的事实、判断和草案；用户可看原历史，已完成训练不被重写。

## 五、研发步骤与独立验收

**阶段 1：建立基线。** 固定一组合成案例，录下现有送模内容、被裁剪项、回答及本机耗时；真实模型/费用没有授权就标 `NOT_RUN`。用旧和新流程共用同一输入，不能先改测试集再比较。

**阶段 2：基础召回。** 修复本人/他人、多意图、去年和日期解析；实现证据依赖闭包，明确“未取到”与“未保存”。测试语义、时区跨年、限制、资料版本和截断。

**阶段 3：版本化结构和校验。** 增加并行 V3 读写与 V2 兼容，服务端持久快照映射短 ID、数值和来源版本；校验缺引用、串人、单位错误、旧版本、伪造来源及未经确认的写入；双端迁移失败不破坏已保存数据。

**阶段 4：回答和中控。** 输出简短结论、关键依据、缺项及可展开的详细数据；正式修改依次执行预览、确认、幂等和持久回执；一个意图失败不吞掉其他可答部分。

**阶段 5：质量与成本核验。**

- 合成测试必须对固定案例中所有标为关键的限制、来源身份、单位、决定性支持/反证给出逐项通过/失败；出现丢失或跨人引用则新方案不得判通过。
- 用同一测试集测问题回答率、个人数值正确率、任务完成率、错误拦截/漏拦截、异常解释；保留失败例子、分母、人工标签以及与旧版对比。评分前由教练/合适的专业人员确认标准，不给未经校准的“专业能力分”。
- 单独记录模型输入/输出 token、调用次数、延迟、失败率与成本；如真实提供商未授权，报告未测，不用字节数替代 token，不承诺节省比例。知识任务、复杂比较、长周期和高风险问题分别看质量与成本，不能以平均数掩盖某类退化。
- 随机将一部分未用于开发的案例保留，测试完成后不改预期以迎合结果。人工评估、真机及长期结果与工程测试分开记录。

**新增需要验证的产品风险：** 现有现代协议要求整段证据原文出现在回答中，而句子级规则把缺乏绑定的个人数字识别为错误；可能增加回复长度或误删有效个人描述，但具体发生率仍需真实模型测量。短 ID 重构必须验证确实减少重复，且不降低来源、数字和越权校验力度。

# 9263254 深度补充：让本机分析低成本、可靠地传给方坤

本节为建议设计和本轮静态审查/合成测试，不代表软件已经修改。用户目标：App 算出的训练、状态、历史及恢复结果，方坤可以快捷读取，用较少 token 给出有依据、直接的回答；关键事实、限制和反证不能为压缩而消失。

## 一、当前有什么，又卡在哪里

1. 当前 `online-context.ts` 已把按问题选择的事实、本机计算/假设、有限对话传到服务端；这比完全不传分析更进一步，但不是把全部 App 数据或整个长期画像完整传给模型。数据最大 32 条、上下文有 48 KiB 和引用内容 4800 字节限制；字节不是模型 token，不能直接换算费用。
2. 历史时间召回可能偏向近期：模拟 15 条今年、1 条去年数据，“复盘去年训练”选中今年近期而非去年。已在前一节复现；应先按用户意图圈定年份或区间，再排序和摘要。
3. 本机分析的支持事实如果没被本次条件筛选，`localAnalysisRecords` 会过滤对应判断；更早的个人基线或反证可能因此不传。须实际链路检查逐条覆盖，不把未传当无异常。
4. 新发现：`online-handoff.ts` 的 `field` 使用 `clean(...).slice(0,256)`，会截断分析解释、建议条件和对话文本。合成测试中一条 310 字观察末尾的“重要反证”未进入 256 字传输；一条 300 字对话尾部的“明日比赛”也未保留，字段没有单独截断标记。证明的是字段级截断风险，不证明某次真实回答一定出错。
5. 长分析的来源 ID、版本、结构字段和重复引用占用预算；模型请求中还使用完整引用核对。**是否能减少多少 token 和费用不能猜测**，必须用同一案例、相同模型与实际计数比较；假服务只能验证内容与处理流程。

## 二、建议方案：计算一次，按问题打包

### 2.1 本机保存完整依据

App 保留完整原始记录、修订、计算公式、输入和来源、判断、支持证据、反证及时间，作为可查账本。将已选训练、长期目标、能力画像、恢复观察分别管理；不把用户的一次表达直接当长期事实，不把历史 PB 当当前能力。相同活动多来源不重复计数。

### 2.2 每次只形成与问题有关的“教练要点包”

每次识别用户在问的内容与时间范围，按本人的数据构建紧凑结构：

- **问题和任务**：例如“昨天的间歇对明天力量有什么影响”；记录具体训练身份、目标日期、多轮指代。
- **关键事实与程序计算**：只包含影响本问的实际训练、分圈摘要、个人参考及单位；由程序计算配速、范围或变化，结果与原记录和版本可追溯。
- **状态判断**：明确这是事实、估计、候选解释还是未知，含支持、反证、数据覆盖和下一步复核；不将生理解释说成医学确诊。
- **任务相关限制**：如已知疼痛、已批准计划和用户时间；明确限制作用的动作范围，不对无关知识全面阻断。
- **缺项与裁剪**：记录未包含的领域、原因、数量及关键缺口；安全限制、选中课次和决定性反证优先，不能在压缩时被默默删掉。
- **用户要的结果**：明确回答、比较、短期方案、长期方向或待确认的操作；多意图逐项回应。

例子（虚构、仅说明结构）：`对象：跑A；事实：4×400米，组间90秒；状态：最近训练累积较多，未有睡眠数据；支持：训练记录；反证：同条件完成稳定；限制：无已确认限制；任务：讨论明天安排；待确认：疲劳感与训练时间。` 数字和条件必须来自实际数据，不能照抄示例。

### 2.3 短标识与按需展开

在一次请求内用短引用 `F1/C1` 连接事实、计算和判断；完整来源、单位、原始值、版本与公式保留在受保护的映射中，供程序核查和用户展开。模型看到的是短标识与足够判断的内容，不能只看到哈希而不知道含义。事实校验需以服务端可信快照和确定性规则核对；客户端计算仍标来源未独立验真。短 ID 每次绑定具体用户和版本，不能跨用户复用或因缩短导致冲突；不允许把旧答案的数字当成新实测。

初次只发要点与必要依据；需要详细分圈或更早对照时，由应用按本问范围获取并补充，用户正常问答不需要额外确认。若无法使用工具补充，提前选好最相关详情并明确未覆盖范围，不假称模型已读全量记录。保持真实服务预算、用户主动关闭及正式写入确认等原有控制。

### 2.4 压缩与取舍规则

- 优先：用户实际问题 → 当前动作相关风险 → 选中课 → 对结论关键的计算/反证 → 目标与相关日程 → 必要历史和对话。
- 将重复事实去重、单位统一但保留原始口径；多段训练可先给概览与极差/关键段，必须能按需回到具体分圈，不能只靠平均值抹掉异常。
- 长文本按语义拆为结构化条目，不在 256 字处直接截断；不可传完时带明确截断和遗漏类型/数量，尤其不能丢条件、反证或安全限制。安全相关文本若无法完整表达，要保留关键约束与需要复核的状态，而不是静默删除。
- 历史、当前状态、目标/预测、实际/计划、本人/他人、不同设备分别标识；一个字节限制不足以证明 token 降低，也不能因极限压缩牺牲问题答案。
- 新资料只使依赖它的判断过期；普通问题及其他无关候选不因无关数据变化而被统一取消。数据更正重算本地依据；不可隐瞒失败或把旧结论当新结果。

## 三、测试与比较：省钱必须同时好用

1. 用相同冻结案例对比现版和要点包：模型实际输入 token、输出 token、费用与延迟；按真实模型的回执统计；本地假服务只验证请求内容和行为，不能宣称真实节省比例。
2. 评估答案是否回答用户、使用正确时间/对象、事实计算准确、关键风险及反证保留、明确缺项和不确定性；对比专家盲评和确定性检查。任一关键安全事实/反证被丢或来源错配，不能因为 token 省了就通过。
3. 至少覆盖长文末尾关键条件、30 分段间歇、一年前相似课、昨天＋去年对比、多设备 HRV、用户朋友混合、无明确选课、多个目标、资料更正、一般科普、服务超时；明确截断后用户仍能获取完整依据。
4. 收集本机计算、筛选、上传、响应和校验阶段的耗时；敏感信息不写进日志。体验目标是用户一次问清楚、直接得到有用答案；不能为追求无等待而展示未经校验的个人事实为已确认。

## 四、继续排查发现和优先级

- P1：自然问法识别不完整，例如“我现在恢复得如何”；历史“去年”检索与选择顺序不匹配；多轮短追问可能丢检索指代。以上有函数级复现，真实发送链须复测。
- P1：本机依据缺少依赖闭包、长字段被静默截断，可能使方坤忽略关键依据或反证。字段截断已合成复现，完整影响范围待核。
- P1：比较两课并同时要求改课，比较分支可能提前结束；需拆分任务，给调课候选和确认，不能假报已执行。

- P0：正式备份恢复、旧标签隔离仍未完成；用户原始数据不得改写或删除。
- 待核：真实设备、Safari、真实模型及付费消耗和专家评价；不从源码或假服务宣称全部通过。

# 9263254 深入复盘补充：历史检索、上下文与中控

审阅基线：旧完整包与 9263254 增量组合的独立副本。用户数据、生产和付费模型未接触；代码未修改。本节优先于后面的此前报告。标注【函数复现】【源码路径风险】【待真实入口验证】，不将风险当作已经在线上必现。

## 一、新发现：去年训练查询可能反而选中今年

**问题（P1，【函数复现】）：** 在 `selectOnlineContext` 构造本人 15 条 2026 年训练及 1 条 2025 年训练，问题为“帮我复盘去年训练”，分析日为 2026-10-28。选择结果只包含最近 6 条 2026 年记录，2025 年记录未进入，`omitted=10`；同一数据问“分析我的2025-03-01训练”，该日记录被优先选中。

**为什么：** `online-context.ts` 将“去年”识别为历史请求，但训练排序主要按新近日期；只有 `YYYY-MM-DD` 被显式提取并加权。引用预算使较旧记录可能被挤掉。`analysisDay` 也只处理明确日期、昨天、今天等，去年默认当日。整条真实 UI→存储→模型路径和该用户记录尚未验证。

**影响：** 用户明明问去年，模型可能看到今年的记录和“部分历史未发送”，却不能用缺失记录回答去年；如模型没说明覆盖可能给出偏题结论。完整保留历史≠检索到了用户要的时间。

**建议：** 使用明确的时间范围解析（去年、前年、去年上半年、上个月、赛季）及本地时区；先在目标范围内筛选，再做适配目的的检索和聚合，向用户显示实际读取范围、记录数及缺失。没有数据说明缺失；按日期筛选不能把去年限制用于无关的当下状态。验证跨年/闰年、时区、过去与现在比较、无数据、多人、旧记录数量多、摘要与模型真实输入一致；必须保护不相关用户隐私。

## 二、新发现：完整事实存在，本机计算仍可能没有交给模型

**问题（P1，【源码路径风险】）：** 在 `selectOnlineContext` 中，`eligible` 已按问题筛选：近期恢复指标只纳入相对分析日约 7 天范围；`localAnalysisRecords(packet,...,eligible)` 仅保留所有引用均在 eligible 的计算/观察。因此一个引用更早同协议 HRV 基线或训练比较的本机判断，即使在本地分析包中存在，也可能因为部分依据未纳入本次 eligible 而不被传递。交接包修好了“能传部分本机分析”，不代表各类计算、基线、反证都能传到模型。

**影响：** 模型可能看到今天 HRV 或选中训练，却看不到支撑“相对个人常态”的历史依据；而该条计算是否被过滤不一定以逐条缺失原因显示。本轮未在真实设备上复现具体 HRV 案例，不断言所有基线判断都丢失。

**建议：** 对本次选择的每条关键判断建立可追溯依赖闭包，携带必要基线摘要、有效天数、时间段与来源修订；未能传递时逐条明确原因，不能仅给笼统预算提示。确保过期、跨人、跨设备、未授权事实不因闭包扩大进入；测试 7 天外基线、换设备、反证、预算截断和修订。不要把客户端申报包装成服务端独立验真。

## 三、新发现：复盘两节并改课可能只执行比较分支

**问题（P1，【源码路径风险】）：** `coach-sheet.tsx` 在 `send` 开头，若文本含“比较/对比”且选了 A、B，就先运行比较分支并 `return`；`prepareR5Command` 等修改识别在这之后。含“比较这两节，并把明天训练改到周五”的混合意图可能只进入比较，不生成调课提案。模型是否会在回答中解释、UI 是否有其他路径补偿，未完成真实入口验证。

**影响：** 用户一次提出比较和调课，看到比较却不知道后半项没有进入操作流程；与方坤作为中控的目标不一致。不能因为识别到修改而直接写课表。

**建议：** 显式拆分意图并追踪每个子任务状态：先输出比较，读日历后给改课预览；目标或时点不明确时只澄清该部分。相关风险和版本校验保留，正式修改需用户确认。验证比较＋改课、训练分析＋营养、他人＋本人、取消和重复提交。

## 四、再看现有问题的严重程度

| **整理训练事实** | 有训练、跑步分段、力量组次、状态和修订等结构。 | 同一手表跑步汇总时长可能被重复计算；训练页错误值是否传播到画像、在线上下文和周统计需逐入口核对。 |
| **分析疲劳与恢复** | `health/recovery-assessment.ts` 结合 72 小时内训练、部分恢复指标、症状及可比历史，给观察、假设、反证、缺项和条件性候选。 | 这些是规则和观察，不是已校准的个人“疲劳百分比”或医学诊断；功能/症状、设备与历史覆盖不全时判断有局限，某些固定规则尚待专业审查。 |
| **分析健康与训练状态** | 能展示可用指标、不同来源和部分同协议趋势；把目标和实测分开。 | 更全面健康状态、跨专项经验、长期能力变化和复杂比赛可行性尚未完整闭环；没有真实长期结果证明分析精度。 |
| **判断用户在问什么** | 支持部分个人问题、选课及风险语义。 | 在未显式选课时，“这次训练怎么样”“我想知道训练能力”等合成输入被 `onlineContextNeeds` 判成非个人问题，相关个人事实可能不进在线上下文；这是函数级证据，真实发送入口仍需验证。 |
| **把结果交给大模型** | 自动联网时，`online-session.ts` 的 `prepareOnlineExplanation` 本地构建包含分析结果的 `packet`，同时构建按问题筛选的结构化 `context`；服务端可处理另一路提供的 `analysisPacket`。 | 当前自动联网的 `runOnlineExplanation` 创建快照时发送 `question`、`declarations`、`context` 和授权，**没有发送所构建的 `packet`**；因此不能说这条自动主链已把完整本地状态判断和候选交给模型。服务端另有 `analysisPacket` 分支，不应误写成全系统完全不存在该能力。 |
| **引用数据回答** | 模型可收到所选上下文和覆盖说明，前后端做事实/权限分类及版本检查；假服务测试了部分链路。 | 模型能否选择正确事实、解释竞争因素、回答用户具体问题，以及是否遗漏个人长期背景，尚没有真实模型和专业评估证据。限制/字节预算、人工/自动选择、短追问都影响结果。 |
| **给出并落地方案** | 代码有周期草案、个人方案、保留原计划、确认写入等能力。 | 现代在线模型指令限制自行新算个人剂量，程序可通过其他路径给出候选；各路径是否共享最新真实事实、是否覆盖同一问题及是否能持续跟进仍待验。生成文本不等于已经写入，也不等于专业准确。 |

### 二、专业教练应具备的完整能力链

1. **先拿对事实**：按用户、时间、活动和来源读取 App 中确实存在的资料；每个重要数值带单位、发生时间和修订，缺失、冲突、裁剪明确列出。同一次跑步跨来源只计算一次，不将计划当实际。
2. **做可复算分析**：由程序计算配速、分圈、训练量和同协议个人参考；分别描述近期训练、全身状态、局部症状、睡眠及饮食。保留数据质量、可比较性、支持和反证，不把单项指标当作健康或疲劳的确定答案。
3. **组成针对用户问题的分析包**：根据问题选择近期与历史、已确认目标、已有计划、个人基线、重要限制和上轮对话，把数据与计算结果及版本一起组织，并说明未读取的部分。必要时进行摘要或分层检索，不能默默丢掉关键证据。
4. **让模型参与判断与决策**：模型针对实际问题解释：当前可确认什么、可能原因及替代解释、下一课/周期的可行候选、为什么、关键条件和下次验证。既要能给实际方案，也不能编造个人数据和无依据的精确剂量。相关数据缺一部分仍答能确定的部分。
5. **复核并按权限执行**：分别检查个人数字与来源/单位是否一致、计算能否复算、建议是否与明确限制或既有计划冲突；保留不确定性和专业转介条件。正式训练计划或数据写入前预览、版本检查、本人确认和回执；普通问答不逐次授权。
6. **真正长期跟进**：之后依据执行、身体反应、纠正及比赛目标变化重新判断，解释为何维持、调整或撤回。数据和判断保留历史，改变事实后关联结论标待复核。

### 三、针对核心目标的验收题

- **状态识别**：给出 14 天虚构跑力训练、睡眠与 HRV、局部酸痛、一次比赛前状态；输出使用了哪些记录、哪些可比、当前信号及关键缺项；安排不把缺 HRV 当作禁训，不把正常 HRV 当成疼痛解除。
- **单课问答**：明确选择虚构手表跑 A，同日还有 B；问“这次训练怎么样”，模型输入含 A 的总量、可用分圈及来源，B 不被当作 A；再问“那明天呢”必须延续正确指代或澄清。测试缺分圈、单位冲突和纠正。
- **中长期计划**：同一 800 米目标，两名运动员成绩接近但跑步/力量经验、训练日历和疲劳不同，应解释不同的起点、近周课程与长期阶段；未来周注明条件，不虚构配速或保证成绩。
- **更正与反证**：更正手表某圈时间后，受影响汇总、引用和判断更新，原回答标待复核；可比表现稳定、主观疲劳降低时能削弱先前疲劳假设，不把无反馈当恢复。
- **质量核验**：记录输入来源与覆盖、各项公式、实际模型收到的内容及完整回答；独立专项教练审核事实、判断、建议及可执行性。长期看冻结前瞻案例对照实际结果与简单基准，分别报告样本、错误和适用范围，不把合成测试或模型自评当准确率。

### 四、实施优先级

先修正事实汇总和选课/个人意图，打通**现有本地分析 → 面向本问的可追溯分析包 → 联网模型 → 可核对答案**；再完善长期画像、专项规则和专业知识。保留现有安全保护与用户确认，优先修复真实数据通路，而非只增加提示词。真实服务上线、付费调用和专业评估各自留待相应授权与环境。

## 2.2 方坤作为整个 App 的教练中控

用户明确：方坤不仅负责回答问题和分析状态，还应成为整个 App 的**统一教练入口与协同中控**。用户用自然语言表达想做什么，方坤应理解意图、读取相关模块、结合情况提出合适的操作或方案，并尽量在对话里完成操作；训练、饮食、健康等页面继续负责详细展示与专业功能。用户不必为每一步在多个页面反复寻找入口。

### 一、现在有哪些基础、还差什么

- `src/components/coach-coordination-hub.tsx` 已有“方坤 AI · 教练中枢”：全局观察、部分待办、跳转训练/健康/饮食等；源码明确该区域主要是**只读摘要与导航**，不是已经具备对所有功能的直接操作能力。
- `src/lib/coach/r5/host.ts`、`r5/commands.ts` 已有部分结构化提案，例如日程、身体资料、体重和症状等；`src/lib/coach/r4/course-flow.ts` 有移动/交换已有课程及冲突检查、确认与撤销。它们是局部基础，并不意味着所有自然语言操作、模块入口及数据一致性都已贯通。
- 在线模型目前无直接写入权限；这不应妨碍中控根据用户意图生成操作候选，再交给现有受控执行入口。多模块数据、真实服务、执行状态、跨页同步和失败恢复仍需核查。

### 二、中控需要能调动什么

| 用户说的话 | 方坤应完成的动作 | 当前设计及权限边界 |
| --- | --- | --- |
| “看看我今天状态和训练” | 汇总训练、恢复、睡眠、饮食和目标，直接回答；可一键打开具体依据。 | 读取与分析自动进行；资料缺失说明范围。 |
| “把明天力量课改到周五” | 查询本人的课表、冲突和目标，给具体调整预览。 | 原课、日期、受影响课次清楚显示；正式写入前用户确认，并有回执与可撤销条件。 |
| “把这节跑步调轻一点” | 找到目标课程，结合训练目的、恢复与限制，提供可比较的调整候选。 | 不能擅自编造剂量或覆盖已执行记录；确认后才写入正式计划。 |
| “把这顿饭改成半份” | 找到对应餐食，展示旧份量、新份量与影响；相关汇总和建议重评。 | 涉及正式记录写入时先预览确认；歧义时只问需要核实的餐食。 |
| “这周以 800 米比赛为主，重新安排” | 联合跑步、力量、恢复、现有日程与比赛日期，给阶段方向和近期可执行候选。 | 先解释取舍和影响；不自动覆盖已确认或已完成历史。 |
| “我今天腰不舒服，明天怎么办” | 综合当前症状、训练目标与计划，给相关约束、候选和必要的进一步处理提示。 | 不因局部问题全局阻断知识；严重信号优先处理，不提供诊断或自动解除限制。 |
| “分析这节手表训练” | 展示明确的活动、来源和所用分圈/心率，给分析并允许打开原始详情。 | 不自动合并不同训练；缺失、冲突或未选择时明确提示。 |
| “这个动作怎么做 / 进入力量训练” | 直接回答常识、打开动作教学或带用户进入相应功能，并保留对话上下文。 | 浏览和导航不需要逐步确认；教学视频不等于个人动作已验证。 |

这些是用户认可的产品方向和拟建设能力，**不是目前所有入口均已实现的声明**。对于查看、筛选、打开页面、生成候选和一般问答，减少不必要的确认；正式计划及记录变更仍执行此前确定的预览确认。账户、费用、模型配置和隐私授权维持明确的状态与保护，不因中控便利绕开身份隔离。

### 三、统一工作链

1. **理解**：识别用户目标、对应训练/日期/餐食、意图类型与主体；不确定时先给能确定的部分，只追问关键缺项。
2. **读与分析**：通过统一接口读取当前有效事实、已有计划、个人状态、长期背景与依赖版本；缺失或冲突明确展示，数据不重复。
3. **提出**：生成简明答案、目标模块入口或可执行操作差异；区分“已读取”“已生成草案”“待确认”“已完成”“失败”。
4. **执行**：只读/导航直接执行；写入调用各模块现有的受控能力，在必要的版本和权限检查后，由用户确认具体变更，避免模型直接改存储。
5. **协调**：已确认的计划或记录变化使受影响的训练、饮食、恢复和画像建议重新评估；未受影响的问题不被全局拦截。后台失败、跨模块部分成功时逐项回执，不假称全部完成。
6. **跟踪与纠错**：用户可查询刚才改了什么、结果如何、能否撤销；只在未覆盖后续修改时撤销，过期或冲突重新预览。原始训练和健康记录保留。

### 四、验收中控是否真正方便

- 连续旅程：问今天状态 → 选择明天一节训练 → 说改到周五 → 比较差异 → 确认 → 课表、方坤与训练页显示同一结果 → 反馈后饮食/恢复依赖标待复核 → 查询或撤销，已开始训练和后续修改不能被覆盖。
- 训练、饮食、健康分别测试“直接看、直接解释、打开详情、修改预览、确认、失败/取消”及状态一致；区分普通问答无需确认与正式写入需确认。
- 测并发和重复点击、人物切换、断网、旧资料、歧义目标、关联手表的两节课、保存失败及跨模块部分失败；不得误报成功、乱改他人资料或因某一模块缺数据阻断无关问题。
- UI 在手机端首屏提供清楚的答案和下一步，具体操作卡就地展示前后差异、受影响项目和结果；设置、来源、技术细节按需展开，操作后仍可回到原对话。

## 3. 新一轮重点发现：和设计理念直接冲突

### X01. 训练关联后的时长和配速可能翻倍（P0/P1：数据可信；截图可见＋函数级复现）

用户训练页截图：上方 6.01 km / 53:43.87 / 约 8分57秒每公里；下方手表 6.01 km / 26:51.94 / 约 4分28秒每公里，时间近两倍，距离未翻倍。不同位置读数不一致，并不证明原始记录被永久改写。

`src/lib/ui/training-read-model.ts` 的 `applyV4Fact` 对合并成员的已知时长直接求和；模拟同一活动的 import 与 Garmin 两条 1611.94 秒记录，输出 3223.88 秒。可能是截图的原因之一，尚缺该用户记录与真实运行链证据。

**目标方案：** 按明确活动身份和已确认关联去重；跑步时间和距离同口径计算配速；跑步、力量、整课和多源记录分别保留。只有有证据且不重叠的不同分项才能相加；来源冲突时明确展示。同步核查训练列表、周汇总、画像、在线依据；保留原始记录。对单活动重复来源、真正两节课、同日多次、跑力组合、未知时长、撤销关联和更正后重算做回归。

### X02. 自然语言未识别为个人问题（P1：理解用户；本地函数复现）

以空的显式选择调用 `onlineContextNeeds`：`这次训练怎么样`、`刚才那节呢？`、`我想知道训练能力`、`跑的长距离，均速4:46，平均心率157` 均返回 `personal:false`；混合句“我的朋友跑了5公里，我跑了10公里，该怎么安排？”也返回 `personal:false`。这说明该选择器会拒绝获取个人背景，**不等于已证明用户那次实际请求的完整行为**；其他本地路径可能回答，也可能存在显式训练选择。

**设计冲突：** 用户自然追问或说自己成绩时，私人教练应该理解谈的是谁、哪一节、要做什么，而不能依赖固定字词才读取资料。**目标方案：** 统一主体、意图、上下文指代及已选择训练；个人与第三人信息分开；不确定时给已有信息的部分回答并只问关键澄清，普通科普不无故读取个人资料。用原句、同义句、第三人称及混合对照在真实发送入口测试。

### X03. 联网模型缺少完整多轮交接（P1：持续对话；源码确认）

`src/components/coach-online-request.tsx` 接收当前问题、人物、选课，`online-session.ts` 构建单轮问题和事实快照；现代服务端模型请求包含当前 `question`、事实和覆盖说明，未见该主链发送最近对话。界面可保留历史，本地路径也可能有对话记忆，但不能等同于在线模型知道上一问。短句“那明天呢”“刚才那节”尤易丢上下文。

**目标方案：** 给每轮绑定本人的相关近期对话、明确指代、已确认的持久信息和版本；区分当前临时描述与已保存事实，不把模型自述自动当事实，控制预算并说明裁剪。测试接续、换话题、第三人、人物切换、更正、重启及敏感数据最小必要传递。

### X04. 明确选课、自动关联与在线依据可能不一致（P1；源码确认，端到端待核）

`coach-sheet.tsx` 先依据特定措辞计算 `selectedIds`，后续才可能自动关联手表活动，而排队仍使用先前计算的值；手动所选也可能因为问题没命中特定词而不随请求发送。最终行为与数据来源须走实际入口验证；用户上一张方坤截图反馈的是 UI 不稳定，不能把它当作实际选课失败的证明。

**目标方案：** 每次发送前确定本人的具体活动和版本，同一次本地、联网与界面统一使用；无唯一目标时询问或说明，不把无关问题堵住。手表总量、分圈、心率、配速只传实际可用的并标出处；同一日期两课不自动合并。

### X05. 私人教练入口存在粗粒度拦截（P1；源码确认）

`src/lib/coach/personal/host.ts` 中个人资料保存超过 30 天时直接要求复核并停止具体方案；最新一次反馈含 pain 时返回“暂停力量和跑步建议”。该函数是**私人教练的一条入口**，不是断言整个产品都如此。按文字和代码看，它没有在此分支区分疼痛部位及拟议动作，也没有先根据具体字段是否变化区分哪些分析仍可答。

**目标方案：** 时间触发复核而不是把所有能回答的任务一律阻断；保留已知限制，按症状严重性、范围及当前活动限制对应建议，未知不假设安全。对过期资料提供条件性结论和补充事项；紧急信号优先给即时应对。复核真实入口与专业适用性后再改规则。

### X06. 能给训练思路，但详细个人量化能力有明确边界（P1；源码确认）

现代模型提示要求不得新算个人剂量，数字事实引用也需满足来源约束；确定性计算和既有候选生成另有代码路径。因此不能简单说“方坤完全不会出数字计划”，也不能认定可以可靠产出任意训练剂量。涉及赛季计划、分圈分析和进阶时，需要核对具体计算、模型调用和正式写入各自做了什么。

**目标方案：** 建立有单位和输入来源的计算服务，允许专业规则支持的条件性候选、多个选项及明确不确定性；无可核依据不编造；模型负责解释取舍，程序校验数值、约束、数据版本。候选可讨论，正式写入仍预览确认。具体剂量和适用范围由合适的专业人员审阅。

### X07. 问答 UI 不稳定和内容泄露（P1；截图＋函数级复现）

用户上一张问答截图反馈 UI 不稳定。代码中回答理由与外层对话分别滚动，输入区又有独立高度限制；这是手机滚动/键盘问题的风险，需 iPhone 真机复现，不能单凭截图断言不可滚动。`digestCoachAnswer` 对跨句 `**结论：……。**` 的合成输入会把开头和结尾 `**` 拆开，已函数级复现用户图里的符号显示。交付方合成桌面与手机截图还显示 `quality`、来源标识等内部字段。

**目标方案：** 把结论、重要依据和下一步放首屏；来源详情可展开；解析格式先于摘要、不要拆断符号；减少嵌套滚动，处理键盘和安全区；自然滚动且切页/收到新回复不抢阅读位置。测长文本、连续回复、加载错误、展开收起、键盘、iPhone/iPad 真机。

### X08. 资料缺失不应变成训练永久禁令（P1；设计及规则待核）

健康与恢复中已有信号、个人资料和旧限制的独立处理，但固定规则及全入口一致性尚未专业校准。正常 HRV 不能抹掉疼痛，缺 HRV 也不能抹掉全部训练知识；轻微症状、过期记录和急性危险信号按性质分开。当前没有足够证据宣称所有规则都错误；建立成对案例及专业审核，避免从单指标推断诊断、因果或某个肌肉的准确恢复百分比。

## 4. 提升方坤的专业教练能力

下列是要建设并验收的能力，**不是声明当前已具备**。必须同时建设数据、计算、专业知识、模型推理、反馈和用户展示，不能仅新增一段提示词。

### 4.1 训练数据与过去一年的历史

- 保存和调阅过去一年及更久的可用记录，包括比赛/PB、逐课跑步、分圈和休息、力量逐组、睡眠、主观状态、受伤限制和目标变化；按发生时间、来源、单位、版本、运动员归属组织。
- 用近期记录判断当前状态，用较早记录识别训练阶段与趋势；历史 PB 是过去实测，当前水平须结合近期可比依据，不把厂商预测、目标、历史最佳和当前表现混成一项。缺少原始历史要诚实标记，不凭聊天编造。
- 多源同一活动去重但保留原始来源；不同活动不合并。历史补录和纠正触发依赖画像/计划重评，原记录与旧结论版本可追溯。对不同设备、算法、测量协议分段比较。
- 代码现有 `online-context.ts` 是按问题有预算地检索；32 条、结构/字节限制及更小的引用内容预算可能裁剪重要记录，须按时间段与任务分级召回，完整性、缺项和保留原因可解释，不能声称现已全部检索。

### 4.2 健康、疲劳与恢复分析

- 同时看训练实际、睡眠、主观感受、疼痛部位和功能、HRV/静息心率、生活压力与饮食；分开全身状态、局部反应、训练表现和数据质量。
- 基于同一设备/协议建立个人参考范围，显示采样天数和可比性；换设备不硬接。支持相反证据，例如 HRV 下降但训练感觉和表现正常，不能单一数值解释成疾病或中枢疲劳。
- 给出已知结论、竞争解释、下一项观察和对具体课的影响；必要时提示进一步专业评估，但不把普通缺测变成整体禁训。记录复查时点、支持与反证，变化时可以保持、修改或撤回。

### 4.3 力量训练和跑力配合

- 分开跑步经验、力量经验、动作熟悉度、器械与目标；专项辅助、增肌、最大力量、爆发力和学习目标分别选课。原有 `personal/planner.ts` 入口目前有最多两天及固定动作/组数等初始模板，这是该入口的具体限制，不能说所有力量入口都如此。
- 读取动作、负重单侧/双侧口径、组次、时间、休息、RIR/RPE 和完成情况；未知不计零，计划不冒充已做。替代动作说明训练目的、器械和差异。
- 与实际跑课、比赛、肌群反应和日程一起判断；先保留关键课目标，再给合理替代或候选。停滞先分析数据、动作熟悉、恢复和执行，再讨论单变量调整；不能因一次表现自动加重。

### 4.4 跑步单课、短期和中长期计划

- 单课理解热身、主课、组/轮、分段和组间/轮间恢复；以同协议历史比较，说明配速、心率、RPE、环境和策略的竞争解释。
- 根据 400/800/1500/3000/5000/10000 米及其他目标、日期、实际能力、经历、生活安排和已有限制规划。近周说明每天任务和可执行条件；8/12/24/52 周提供阶段目标、重点、转换条件、复核点、备选与不确定性。
- 比赛提前、漏练、疲劳、工作时间变化、器材不足等触发有依据的候选重排；不强制追回每一课、堆叠双课或改写已完成历史。当前已有周期草案、阶段条件和首周确认机制；还需真正把连续执行与个体反应接到阶段切换判断。
- 可支持用户偏好的 3 周训练加 3–4 天调整，作为**经用户确认的个体偏好**并随实际反馈评估；不把它写成适合所有人的统一生理规则。

### 4.5 饮食与训练协同

- 明确减脂、增肌、维持或表现的优先级；结合训练课、时间、就餐条件、预算、过敏和完整度给可执行候选。
- 区分已记录食物与全天摄入、活动热量与总消耗；缺失不是零。食物识别和份量估算应能修改，修正后关联汇总和补给建议重算。
- 跟踪体重趋势、训练表现、饥饿和恢复，必要时提出复查；不能从单日体重或一餐断定长期能量缺口，也不能由 App 自行诊断低能量可用性相关疾病。

### 4.6 知识不足时怎样真正提升

1. 建立分领域知识库：跑步专项、力量、周期化、健康/恢复、运动营养、设备数据、沟通和风险。每条知识标原文来源、版本日期、适用人群、条件、证据级别、冲突和复核时间；不以数量替代质量。
2. 选用最新可核查的一手共识、系统综述和专业指南；专项差异、年龄、人群与训练阶段匹配后才转为产品规则。文献是群体证据，不直接等于该用户的训练剂量。
3. 把知识转换成可执行的任务合同：输入、缺失/冲突、计算方法、允许的候选、停止或转介边界、解释、复查点及数据版本；与现有模块对接，不另造无法调用的知识库。
4. 把同一用户的长期事实与专业知识分开：前者可纠正撤回、尊重来源和时间；后者按证据更新。模型不能把一般资料写成用户事实，也不能在无来源时宣称联网搜索过。
5. 建立固定测试集：跑步/力量/恢复/营养、不同经验、缺失与反例、历史更正、计划冲突、多轮追问、风险分流；由可复算断言、教练盲评及真实长期反馈共同检验。专业内容审阅与代码测试分别留痕。
6. 知识更替时记录影响范围、测试结果、发布版本和回退路径；变更后旧结论标待核对，避免悄悄改变已确认计划。外部网页检索、付费调用、数据发送及上线需按实际授权与可用性实施。

### 4.7 科学依据起点与适用限制

- [2026 ACSM 抗阻训练立场文件](https://pubmed.ncbi.nlm.nih.gov/41843416/)：总结健康成年人抗阻训练不同目标的证据；用于建立力量知识框架，不应将群体结果直接硬套给中短跑运动员或特殊人群。
- [IOC 运动负荷与伤病风险共识](https://pubmed.ncbi.nlm.nih.gov/27535989/)：支持将训练、比赛和心理负荷及个体状态结合监测；不是靠单一指标推算个人伤病或加减量的公式。
- [2023 IOC 相对能量不足共识](https://pubmed.ncbi.nlm.nih.gov/37752011/)：供营养和健康风险知识核查；不能凭一条饮食记录或单个阈值由软件诊断。

以上是首批参考而非文献全面审查；具体专项训练剂量、康复/医学、特殊人群和个体反应的规则须另作证据审查与专业评估。

### 4.8 判断需要多少数据、多久的数据，怎样证明判断可靠

**核心原则：** 不同判断所需资料不同，没有“只要收集 14 天就一定准确”的通用公式。单课可以用当天完整资料作描述；个人常态、训练耐受和成绩预测需要重复且可比的观察。资料不足时先说能判断的部分和关键缺口，不要求为了聊天先填完整问卷。下面的时间是**研发与采集的建议检查窗口**，不是科学认证阈值、医疗许可或对每位运动员的保证；最终要用实际数据和独立验证校准。

| 要判断什么 | 起步最低数据：能回答什么 | 为提高可靠性建议补充多久/什么 | 仍不能直接得出的结论 |
| --- | --- | --- | --- |
| **一节跑步发生了什么** | 本人一节实际记录：日期、距离、计时口径；有间歇则要分圈、组/轮、休息、完成情况，来源和单位可查。可算总量/分段，但缺项明确显示。 | 可比条件下另外 2–3 节作为**初步参考目标**：同课目的、距离、休息、地形、设备及尽力程度；跨度随实际训练次数，不强制几周完成。 | 只靠一节不能稳定判断专项短板、疲劳原因或比赛成绩。 |
| **当前状态与下一课候选** | 已批准课表与目标、近几日实际训练和当前疼痛/身体功能；睡眠、疲劳感及生活压力按可得性加入。明确重要资料缺失。 | 产品回看窗口可先设近 **7 天**，必要时扩到 **14–28 天**检查积累；是默认检索窗口，不是恢复诊断标准。对某项训练反应记录课后当天和后续 1–3 天（若有），并结合下一次实际反馈。 | 未记录不等于无疼痛；无 HRV 不等于不能回答；好分数也不能覆盖明确限制。 |
| **睡眠、HRV、静息心率个人常态** | 1 天只能描述该天测量，带设备、算法、单位、测量时段；不能称稳定基线。 | 先尽可能积累同设备同协议 **2–4 周的多个独立测量日**，展示实际天数、覆盖、波动和测量条件；再观察更长阶段和换设备分段。2–4 周是工作起点，不是保证稳定，也不代表每天必须测或第 14 天就可诊断。 | 单次偏离不证明疲劳、疾病或训练导致变化；设备更换或持续恶化不能简单并入“新正常”。 |
| **跑步专项能力与近期水平** | 已确认的近期比赛/测试或具有清晰目的的实际训练，保留距离、时间、日期、条件和测试类型；至少能描述这些表现。 | 可检索近 **4–12 周**相关训练和近期同项目比赛/测试，并调用更早可靠 PB 和过去一年训练背景；这是建议回看范围，不是成绩预测的统一科学门槛。根据训练密度和专项实际调整。 | 目标、手表预测、历史 PB、间歇训练成绩与当前比赛实测不能互换；没有足够可比证据时不输出伪精确秒数。 |
| **力量经验、水平与进阶** | 至少该动作的真实训练记录：动作、重量口径、组次、完成情况和器械；RIR/RPE 有则记录，缺失不当作零。 | 尽可能取得 **2–3 次同动作、相近协议**及其训练后反应，分布在运动员的自然训练周期；同时记录跑课与恢复。达到次数仍须判断是否可比。 | 不靠一个估算 1RM 概括爆发、动作技能或长期耐受；不能自动加重量。 |
| **个人对训练的反应** | 一次课及后续反馈只形成观察线索，保留其他训练、睡眠、环境等干扰。 | 目标是多次类似暴露、可比课和对应的课后及后续反馈，并保留表现稳定或相反的反例；样本少或条件变化大就持续标记不确定。 | 即使有 2 次反馈也不能自动推广到不同强度，更不能由相关性认定因果。 |
| **饮食与补给** | 一餐可评价已记录食物及不确定份量；不知道全天覆盖时不能判断全天赤字。 | **3–7 天**可作为寻找常见餐次和执行障碍的初步记录窗口，覆盖不同训练日/休息日更有用；体重趋势需多次、相近条件测量并随时间复核。窗口是产品探索建议，不保证估计准确。 | 一餐、一天或漏餐记录不能当全天长期真实摄入；手表活动消耗不能与总消耗重复相加。 |
| **中长期目标与周期** | 项目/目标日期、近期可核实训练与比赛、实际可训练时间、器材和限制；缺项时先给阶段方向与条件候选。 | 最好补齐最近 **4–12 周**训练执行及跑力经历，并查看前一年重要赛事、阶段变化、伤病与训练中断；过去一年是背景，不是必须全量上传，也不替代近期状况。结合每周实际和后续反应滚动更新。 | 提供完整周数不代表有足够依据预测成绩或保证周期有效；未来周为条件草案。 |

**准确程度如何表达：** 每个判断同时展示①结论和适用任务；②数据来源、时间、关键值与覆盖；③支持证据和反向证据；④有哪些缺项或不一致；⑤下一步怎么验证以及何时复核。用“描述事实 / 初步线索 / 多次可比支持 / 外部验证”表示证据阶段，不输出无法校准的“85% 准确率”、虚构概率或医学意义上的可信区间。

**怎样检验依据是否经得起验证：**

1. **数据链核对**：合成和经授权的真实样例逐项比对手表原始记录、导入、训练页、画像、联网请求、回答和统计；校验来源、单位、时间、分圈和修改版本；同一次训练跨源不重复计量，错误或未同步的信息不当成确定事实。
2. **数值可复算**：距离、时间、配速、力量容量和营养总量由确定性计算执行，保留输入与公式；小数与取整口径分开。答案引用每个个人关键数值时能追溯到对应记录或经核算的派生值。
3. **反例与时序**：低 HRV 但表现稳定、相同成绩不同跑力经验、错误手表读数、缺餐、朋友成绩、更正旧记录、两节同日课等都要分别测试。做回放时只使用当时已知数据，不能偷看后来的比赛结果。
4. **前瞻和独立评估**：先固定问题集与预期评分规则，再由有相应项目经验的教练或专业人员独立评估正确性、依据、可执行性和不合理建议；分开测普通回答、风险识别和个体化能力，记录失败与分歧。专业评估不能只依赖另一个模型自评。
5. **预测兑现与范围**：只有有足够真实赛果/测试、相近适用人群和独立保留的后续数据，才衡量成绩预测误差与区间覆盖；报告样本量、误差分布、失败案例、数据不足人群及对比简单基准，不能用训练集自测宣布精确。样本不足就不发布数值精度声明。
6. **变更后核验**：数据修订、设备切换、训练目标或知识版本变化，检查判断失效和重算；保持历史结论、实际执行及用户确认的记录。建立回滚与上线前/上线后对比，不因通用题通过就宣布长期效果。

**资料选择与取舍的参考来源：** [运动员主观状态监测系统综述](https://pubmed.ncbi.nlm.nih.gov/26423706/) 支持将适合的自报告与其他指标共同考虑，但不证明其对每人的诊断能力；[HRV 引导训练的系统综述](https://doi.org/10.1111/sms.13802) 强调标准化和混杂因素，所纳入基线时间并不一致；[运动中可穿戴心率精度研究](https://pubmed.ncbi.nlm.nih.gov/28709155/)提示不同设备和运动条件可能有差异。上述并未证明表中的产品窗口是精确度保证，具体规则仍需科学和专业复核。

## 5. 分组整改顺序和验收

| 顺序 | 工作组 | 应达到的结果 | 不能误判为完成 |

## 七、补充：方坤问答页面 UI 和训练引用链

用户澄清：上一张方坤问答截图反馈的是问答页面 UI 不稳定；截图本身不能作为训练记录页关联错误的证据。下文的关联代码风险属于独立静态排查，尚不能断定就是用户观察到的原因。训练记录页实际问题见第八节。

### 7.1 现象和证据

用户反馈问答页面 UI 不稳定。方坤问答截图中底部显示“联网分析 开 · 未关联训练”，回答同时引用约 14,041.5 米长距离、3×200 米训练及前一天主观反馈，并出现“看理由（17句）”、`**结论` 等显示。截图不能证明手表详情是否真的发送、用户之前是否已选择或切换记录，也不能仅凭文字证明这些训练属于同一节或同一天。截图属于用户实际界面；本轮没有读取用户私有训练数据、设备日志或真实模型请求。

### 7.2 已从源码找到的关联风险（P1，源码确认；截图具体触发原因待复现）

- `src/components/coach-sheet.tsx` 在 `send` 开头根据问题是否包含“复盘”“这节”“这次训练”等及 `selectedOccurrenceId` 计算在线请求 `selectedIds`；即使用户已选某节，问题措辞不满足判断时，也可能发送空选择。后面才针对某些复盘场景进行默认关联，线上排队仍使用前面计算的 `selectedIds`，存在自动关联的结果未传入同一次联网请求的时序风险。
- `src/lib/coach/online-context.ts` 有选择训练后的本人归属、匹配及遗漏说明；当选择为空，会按问题选择相关本人记录。因此，底部“未关联”并不自动证明模型完全没有读任何历史，但也不能证明它读到了用户指定的那一节及完整手表分圈。
- 手表原始活动、确认导入后的 `confirmedImportId`、训练事实及计划项可能是不同身份；必须沿来源身份与映射核对，不能凭日期、距离相似便合并。自动挑选最新佳明活动仅覆盖特定情况；其他设备、未确认或没有映射的手表记录需另行核查。

### 7.3 展示问题的本地复现（P1）

`src/lib/ui/coach-answer-digest.ts` 先分句再抽结论，`CoachAnswerView` 再去除完整成对的 `**`。本轮用合成回答 `**结论：……。**` 运行 `digestCoachAnswer`，得到的结论以 `**结论` 开头，理由中另有独立的 `**`，与截图显示的符号问题一致。拆句可能先把 Markdown 配对截断，后续清理无法匹配；此项是本地函数级复现，不能单凭它断定截图运行的线上版本与这份源码完全一致。

`src/components/coach-answer-view.tsx` 还在外层对话滚动区域中给理由设置 `max-h-[42dvh] overflow-y-auto`；截图显示理由区域部分内容不可见。嵌套滚动是可核查的设计风险；本轮未在用户 iPhone 现场验证是否存在真正无法滚动或丢失内容。

### 7.4 建议解决方案和验收

1. **先确定具体哪一节**：从训练记录页面进入方坤时，携带用户选择的稳定训练身份；明确显示日期、项目、距离、来源以及“已关联/未关联/资料不完整”。用户可更换或取消，跨人物或来源冲突禁止静默绑定。未选到记录时可回答一般问题，个人化结论应说明依据范围。
2. **本地与联网使用同一份本次选择**：在发送前完成关联决议，再冻结本次请求的用户、训练身份、版本和来源；在线与本地分析共享它，普通措辞不能丢失用户明确选择。两节比较时保留各自身份，后续用户切换不篡改已发送的问题；如需要更正或记录更改，原回答标记过期并可重算。严禁自动合并相近的两节。
3. **手表数据完整且可追溯**：把该节已确认可用的总距离、时间、配速、平均/分段心率、分圈、恢复和其他实际存在的字段按单位传入；明确原始来源、同步时间和缺失、冲突、截断，不推断未记录的组间休息、RPE 或分圈。用户输入的均速和心率与手表数值冲突时分别显示并请求核对；计划、历史记录与本节实测分开。
4. **分析依据与结论**：回答首屏写明正在分析哪节、实际用到了哪些关键数据，以及缺失部分；下一课建议须结合近期负荷、训练目标、个体心率/训练背景和恢复状态，不能只凭均速与一个平均心率给确定的个人强度分级。信息不足可以给条件性解释和观察项，不因缺数据把正常问题整段拦截。
5. **展示修复**：安全地先处理模型常见 Markdown 或使用可靠的结构化渲染，再提取结论，保留完整语义；避免重复“下一课”标题。理由使用清晰可展开的单层滚动，确保手机上整段可以读完，保留原文，不把界面格式修复当作分析正确性的证明。
6. **针对性回归**：用虚构手表训练 A、同日独立训练 B、前一日训练 C：A 的总量与全部可用分圈经选择到达真实在线假服务请求；“跑的长距离”“这节怎么样”等不同说法保持选中 A；不选择时明确状态；同日 B 不混入 A；用户换人、取消、纠错、重试或请求中更改数据时不误绑；缺分圈/来源冲突显示不足；模拟长文本、配对/跨句 Markdown 在桌面及 iPhone Safari 能完整显示。跑相关单元、真实发送入口、假服务和真机测试分别记录。

此问题属于“训练记录与设备数据联动 + 对话 UI”独立工作包，优先级 P1；未进行真实账号或付费模型测试，也尚未修改代码。

## 八、训练记录页：关联手表后汇总数值不一致（用户补充截图）

### 8.1 用户截图实际显示（P1，截图证据）

- 顶部训练记录：6.01 km、53:43.87、配速约 8分57秒/km。
- 下方同页面手表详情：6.01 km、26:51.94、配速约 4分28秒/km；已关联手表的计划比较卡显示约 27 分钟、4分28秒/km。
- 顶部时间与手表时间接近两倍（53:43.87 与 26:51.94 的两倍相差约 0.01 秒），距离没有相应翻倍，显示的顶部配速也随用时近似翻倍。截图支持同页面口径不一致；不能仅凭截图证明源记录、数据库或所有下游统计都已被永久写错。
- “计划没写距离/时长，无法比较”与此异常应分别核对；前者可能是目标缺少字段的正常提示，不能将两者直接视为同一故障。截图的历史整课标识，也不应强行假定手机整课时长与手表跑步时间必然完全相同，或把整课时长当跑步配速分母。

### 8.2 本地代码定位与模拟复现

`src/components/training-log-v76.tsx` 的顶部使用同一行 `distanceM` 和 `durationSec` 计算显示配速。手表详情由 `src/components/garmin-log.tsx` 显示设备原始 `dist`/`dur`。两处数据来源不同。

`src/lib/ui/training-read-model.ts` 的 `applyV4Fact` 在合并成员多于一条时，将每个已知 `durationSec` 直接相加；没有在这一段先区分同一跑步的重复来源与可以相加的不同分项。本轮使用**虚构的**两条 RUNNING 成员（import 与 garmin，身份表示同一活动，各 1,611.94 秒、距离 6,010 米）直接调用该函数，得到 3,223.88 秒，计算配速约 8分56秒/km；应保留单次跑步的 1,611.94 秒，而不是加两次。这是函数级已复现的潜在根因，与截图现象吻合。用户那条记录的实际成员、版本和关联路径未检查，因此不能断言这就是唯一原因或直接改写用户记录。

### 8.3 修复要求

1. 以稳定活动身份和用户确认的关联判断重复来源；同一活动的多份记录只记一次，保留各来源和冲突；相似日期或距离不足以自动合并。
2. 为跑步实际距离、跑步计时、分项用时和整课总时长建立明确语义；同一跑步的配速只用对应跑步时间/距离计算，不能用整课时长或另一个来源的总计。多来源冲突要展示来源和待核值，不能选个值假装确定。
3. 跑步与力量是真正不同分项时分别显示；只有明确不重叠、单位/时间口径一致且有依据的时长才能汇总，未知保持未知；避免从历史整课推断分项。
4. 将日志列表、详情、周汇总、教练画像及在线上下文的读口径逐一核对，避免前台修好而下游继续双算。修复为可追溯的读取投影变更，保留手表和手机原始数据；如确有错误派生缓存，受版本约束重算，不删除或改写用户原始记录。
5. 测试：同源重复导入和跨源用户确认匹配、单独跑步、真实跑力组合、不重叠/重叠、未知分项、冲突及取消关联；6.01 km / 26:51.94 的详情与顶部跑步指标一致；27 分钟显示属于取整口径，不能因取整误报冲突。检查关联前后、刷新、周汇总和人物切换；真实手机 Safari 另外验收。

本轮仅定位与模拟复现，尚未修改代码或访问用户设备。
