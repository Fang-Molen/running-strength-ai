每条失败至少记录测试版本/提交或源码包哈希、题号/路径/轮次、请求 ID、时间、模型及实际参数、输入证据包的脱敏快照或哈希、来源 ID/版本、模型响应状态与 finish_reason、可获得的 token usage、解析/过滤/控制器阶段、预期/实际及原因；任何服务端不返回的数据记“未知”。不要求或保存隐藏思维链，不记录 API 密钥或未授权的隐私数据。记录哪些 token 口径已经包含推理，防止重复相加；账单与 API usage 不一致时分开列示。当前仅掌握用户汇总，不假造逐题日志、具体模型参数或逐类错误数。

## 1. 用户最终要得到什么

方坤作为私人教练和中控：①用手表与手动记录尽量完整认识用户；②了解与本人历史相比的变化；③结合跑步、力量、睡眠、饮食、主观感受和目标给出有依据的解释及可执行选择；④让用户直接查看数据、快捷反馈，并在确认后联动计划与记录；⑤遇到不足或冲突，说清还能回答什么、缺什么、下一步如何补。

输出链：**原始事实 → 可比性与质量 → 个人参考 → 近期观察 → 多种解释 → 用户选择/建议 → 实际反馈与修订**。历史数据、计划数据和实际完成、算法计算与模型推断要分层；缺失不当成 0。原始历史依用户管理策略保留，不以检索评分低为由自动删除。

## 2. 数据从哪里来，如何保证能用

### 2.1 接入和事实模型

手表/健康平台、手机、手动登记、训练计划、用户反馈、饮食各为独立来源。能接哪些品牌与字段须以各平台当前授权、接口和项目实际实现核实；不能把“预留适配结构”标为已支持同步。

每条记录保留 `user_id`、来源/设备、源活动 ID、类型和指标定义、单位、发生时间、记录/同步/修订时间、时区、测量协议、有效性与原始引用；活动另区分总时长、运动时长、整课时长、休息、计划和实际。体力、压力、训练效果等厂商专有分数以品牌与算法版本标注；不同品牌、定义不明或设备升级的数值不直接合并比较。数据原始单位保留，标准单位变换记录可追溯。

身份隔离、权限与用户主动更正优先级明确；用户可查看来源与撤销/更正；同步幂等。离线、无权限、未佩戴、未同步各自展示，不能推断用户没运动。无手表用户仍可用手动和主观数据获取条件性回答。

### 2.2 活动去重与截图问题

同一个运动既有手机记录又有手表记录时先建立关联关系，而不是物理合并所有字段。判断关联可参考时间、运动类型、地点、距离等，冲突或不确定时展示候选让用户确认；一次实际活动仅计一次，分项和整课不能重复加总。关联、取消、重关联、补录、更正都要触发相关汇总及基线重算。

用户截图中：标题处显示 6.01 km、53:43.87、8′57″/km，关联卡及手表详情显示同距离 26:51.94、约 4′28″/km。这可能来自不同记录或时长口径，截图不足以确认根因。开发时先复现和查来源，显示“手机记录／手表运动／计划”的各自距离、总时长、运动时长、配速与来源；不把 53:43.87 和 26:51.94 自动相加或静默覆盖。6.01 km ÷ 26:51.94 的配速约 4′28″/km；6.01 km ÷ 53:43.87 约 8′56″/km（截图显示 8′57″，可能存在距离精度或取整差异）。仅算术大致一致不证明哪个才是用户整课真实用时。用户确认字段后，标题、详情、曲线、方坤应一致；显示保留原始来源与冲突说明。

### 2.3 质量与生命周期

质量标识至少包含 `VALID / PARTIAL / MISSING / CONFLICT / INCOMPARABLE / STALE`，标识数据状态，不是生理健康等级。迟到同步、撤销、改时间/时区、删除、设备切换按依赖刷新；当重算尚未完成，界面标明“更新中”，不显示旧数据为最新。历史回放按当时已知版本 as-of 防未来信息；删除传播遵从隐私设置与既有合规规则。用户切换账号后草稿、查询和缓存隔离。

## 3. 方坤原创个人动态基线 V1

### 3.1 五类基线

| 类型 | 典型信息 | 比较时必须注意 |
|---|---|---|
| 恢复相关 | 静息心率、夜间 HRV | 指标定义、睡眠/晨测时间、设备与算法；HRV 不跨协议强行混合 |
| 睡眠 | 时长、作息、主观睡眠 | 跨午夜按约定归属；设备睡眠阶段为估计值 |
| 主观状态 | 精力、训练意愿、酸痛、疼痛 | 量表含义一致，疼痛部位单独记录；缺失不等于无症状 |
| 训练与表现 | 跑步课型、实际训练量、力量动作组次、RPE/RIR | 同项目、同课型、相近条件；计划与实际分开 |
| 生活与目标 | 工作压力、疾病、旅行、训练周期和目标 | 作为背景和候选解释，不能直接算作疲劳 |

同一成绩不等于相同耐受；群体参考与训练目标不能冒充个人实测基线。一般稳定区间也不等于健康状态或训练许可。

### 3.2 定义时间窗与启动条件

以用户本地分析日 D 为锚，日常指标参考示例默认：历史 D-35 至 D-8 共 28 日；近期 D-7 至 D-1 共 7 日；D 的当前值单列。区间按用户本地自然日闭区间计算，时区变化及跨午夜由协议归属，数据修订按 `knownAt` 区分。比较窗口不重叠，避免把被分析的近期变化吸收进历史。不同问题可设置合适窗口，参数统一版本化。

| 参考窗口内有效独立天数 | 输出 | 近期数据要求 |
|---|---|---|
| 0–6 天 | 展示已有数据，标记基线待建立 | 不捏造参考 |
| 7–13 天 | 初步个人参考，显示覆盖天数与起止 | 近期至少 3 个不同有效日才计算近期中位数 |
| ≥14 天 | 可展示参考及覆盖，仍然不代表已验证预测 | 同上 |

28/7 和 7/14/3 全部是工程起始参数，不是科学上证明适用于所有指标和人的最佳值。若参考只覆盖一段短时间、数据集中在同一周或存在大量缺失，应显示时间跨度和覆盖，供评估，不把“14 条”直接宣称精准。安装前的同口径历史可回填，新用户逐步建立，不要求固定等待 35 天。专项课不按日指标门槛：只用相似课型的可比训练，显示记录次数、时期和差异，少量数据只能描述。

### 3.3 计算与展示细则

1. 按 `user_id + metric + protocol_key + local_day` 选择有效日记录；同日多个来源按可见、可配置的来源规则处理。不能确定来源时记录冲突，排除该指标计算但保留原始值。
2. 有效参考值求中位数和 25%、75% 分位数，使用一致的 R-7 线性插值；近期满足条件求中位数；差值 = 近期中位数 − 历史中位数。样本数不足不计算区间或趋势，结果为 null，不填 0。
3. 用户能看到时间范围、来源、有效天数/可能天数、最近同步、指标口径。过去常见范围不是健康界限；偏离区间只表示与个人记录有差异。
4. 默认参考随分析日按规则滚动，但保留版本化历史快照和关键事件标注，比较长期漂移；疾病、熬夜或高负荷日不自动删除，也可按事先定义条件展示含/不含事件的两个描述性视图。长期不佳、换设备、长时间中断或训练阶段转换时提示重新评估参考；不能默默当作已恢复。
5. 训练后反应用训练结束时间作锚，按可用数据看此前及随后不同时间，不与按日基线混淆。若没有时间戳或训练未完成就说明不能精确匹配。

合成算例：历史 52、53、54、55、55、56、57 次/分，中位数 55，R-7 四分位数 53.5–55.5；近期 57、58、58、59、59、60、61，中位数 59，差值 +4。这里只能说“近期比历史高 4”，不能由此诊断疾病、给出疲劳百分比或判定训练是原因。

## 4. 训练负荷、疲劳与恢复：让方坤真正能用

### 4.1 跑步与力量分开计算

- 跑步：距离、实际时长、强度与课程类型；同类条件的配速/心率/完成度，标识地形、天气、休息和计时方式。
- 力量：动作、肌群、有效组、次数、重量口径、RPE/RIR、休息；自重、等长、跳跃不可硬算外部重量。`重量 × 次数 × 组数` 是特定口径的外部容量，不是肌肉疲劳。
- 整课 sRPE = 完整整课分钟数 × 整课 CR10 RPE，显示为 AU。只在明确范围和可用数据存在时计算；跑力混合课只有整课 RPE 时只计算一次整课值，不复制给跑步和力量。
- 各项负荷曲线分别显示，不把公里、kg·次、sRPE 与厂商专有负荷任意相加；不将急慢性负荷比或任何单条曲线说成精确伤病风险。

### 4.2 恢复分析的四个面向

1. **全身线索**：可比的静息心率、HRV、睡眠及主观精力，与各自个人参考比较。
2. **局部线索**：部位、性质、疼痛/酸痛、时间和影响；明确区分肌肉酸痛与疼痛。
3. **训练执行**：相似任务表现、RPE/RIR、完成度、课程间隔、近期跑力安排。
4. **其他解释和质量**：设备变化、漏戴、生活压力、作息、饮食、生病、气候等。

输出事实、可能解释、相反证据、关键缺项和下一观察；用户主观状态与设备不一致时两者都保留。基于观察提出维持、降低强度或等待补充信息等可选方案并说明原因，原计划变更展示差异并由用户确认。明显或持续不适应建议专业评估；不可自动作诊断、预测伤病或仅因一项正常给复训许可。未经针对人群的校准和验证，不呈现“疲劳 73%”“体力 80%”等精确身体状态。

压力显示区分用户主观生活压力和手表厂商估计压力；如果压力和 HRV 源于相同传感信号，不算两项独立证据。睡眠分期可看趋势和来源，不当实验室测量或疾病诊断。

### 4.3 教练计划与闭环

围绕用户目标、项目、水平、训练历史、时间与器材等制定短期课和中长期阶段方案，明确阶段目标、关键课、跑力安排、阶段复查和根据反馈修订条件。400/800 米专项、长跑、力量增肌及控重的优先目标不同，不能套同一套模板。实际情况变化时提出不同方案及理由；不凭状态分高自动加量，漏课不自动堆积补课。饮食根据目标与训练日情况提供范围/食物选择，记录缺失不得当完整摄入。

## 5. 数据可视化与全端联动

### 5.1 一眼看懂的首页卡片

首屏分三部分：①“近期有哪些变化”：列 1–3 个最相关、可比的事实；②“训练与个人感受”：显示最近关键实际课程与缺项；③方坤建议和行动，如“查看依据 / 补充感受 / 查看训练”。不根据尚未验证的阈值生成“正常、危险、已恢复”等诊断式标签；可显示“数据不足 / 初步参考 / 有可比较记录”等数据状态。

示例（虚构）：近期心率中位数 59 次/分，历史参考 55；睡眠可用 4/7 天；昨日专项跑；腿部感受未登记。方坤：“近期心率偏高，原因还不能确定，可以补充腿部感觉。”

### 5.2 曲线、参考带与时间轴

- 一个指标一张图或一个独立小图：横轴日期、纵轴单位；点线为实际记录，带状区域为历史 Q25–Q75，虚线为中位数。屏幕文字注明这是截至当前分析日的参考及其日期。7/28/90 天切换只改变可见区间，不偷换基线参数。
- 缺失断线、冲突标记、设备更换分段；不插值伪装真实数据。不足以建立参考时展示原始数据和“建立中”，不画伪造区间。回看历史时使用当时已有的快照或可复算的 as-of 结果，不用今天数据冒充过去。
- 按日对齐显示睡眠、心率、HRV、个人感受；各自单位和坐标独立。训练时间轴标记专项、轻松跑、力量及休息，点选可查看真实课程、相关来源和纠正入口。
- 训练负荷图与身体指标图上下联动，但视觉上明确“训练做了什么”和“身体观察到了什么”；前后变化不能被直接表述为因果。分日、周展示时明确汇总与覆盖，当前未完成周期不能和完整周不加说明地比较。
- 图下列出参考日期、样本数、数据质量、同步时间及历史区间含义；图点可点开日期、来源、原始值、算法版本与关联记录。颜色加图例、形状、文本，支持色觉差异，屏幕阅读器有等价列表。

### 5.3 页面职责与现有 UI 问题

健康页看变化与个人参考；训练页看计划、实际与来源差异；方坤页解释及调整方案；桌宠登记精力、酸痛、饮食等快捷信息并写入同一数据源。饮食保留输入框、本地库快速查找及可用时联网查询，来源和估算标识清楚，用户确认份量；查询失败保留手填和草稿。

问答页面针对用户截图进行移动端复现：长内容可滚动、折叠依据区域不截断、不出现原始 Markdown 标记，输入栏与底部导航不遮挡，键盘弹出和安全区下仍可使用。关联训练的选项须显示真实状态，普通问题不因未关联训练而拦截。网络分析保持用户的默认开启意图；当前服务、搜索工具或身份有问题时显示真实错误和重试，不虚称已联网，不能由模型调用推断实时检索成功。

## 6. 记忆、检索和 Token

用户提出的信息价值分级用于**找信息的顺序与摘要粒度**，不用于自动删除。专项关键课、测试成绩、伤病、目标变化等可提高召回；慢跑、力量和日常恢复即使单条优先级低，长期统计时仍必须完整纳入。用户点名旧日期或问全年趋势时，范围查询覆盖所有合格记录，不只挑评分高的。

建议输出紧凑证据包：用户问题/目标、时点和限制、对应个人参考与近期变化、相关实际训练及数据版本、缺项/冲突/反证、证据 ID 和可按需查询的路径。程序先算事实，大模型负责解释、追问和组织方案；按问题动态检索，无需每轮传全部历史。用户更正后撤销旧结论并使缓存失效，旧回答标注过期或重审。

对比全历史与摘要加按需取数时，分别记录调用次数、每次和全对话 input/output/cache token、耗时、费用（无法获取则标未知）、证据遗漏、答案质量、跨轮一致性。不能只追求 token 降低而丢失疼痛、反例、身份或指定历史。

## 7. 验证路径：先用你正在做的测试

### 7.1 接收现有测试结果后

以第 0A 节的用户同步结果为真实首轮基线，收集当前源码提交或包哈希、测试日期/配置、40 次请求的脱敏逐次记录、原始题面与答案、控制器拒绝原因、3 组历史对照及未测项。先将既有公开题、历史失败和用户截图映射到下面的验收点，不重复造同一题；基线不可获得就标 NA，不虚构改进。把未执行、模拟、真实设备、真实模型、专业评审分开报告。复现失败后先处理数据/来源/代码，再检查模型和 UI；修复后回归原题和相关题。

### 7.1A 首轮缺陷专项验收及省 token 复测顺序

**第一步：确定性离线检查。**无需付费模型先复算原题、核对题面/引用契约；用可重放响应覆盖正文为空、截断 JSON、正常 JSON、服务失败、过滤断句、最新事实与反证等。检查控制器接受和拒绝的原因，确保未完整的内容不会伪装成完整成功。题目或参考答案有误时保留原题、记录修订理由与版本；重新统计时分别列原版与修订版，禁止静默改分。

**第二步：小规模真实链路冒烟。**沿用正在进行的测试任务先选 2–4 个来自原始失败的代表案例，至少覆盖截断和证据/来源问题；具体题号由测试组按日志选定。实际通过 App 集成链路调用，记录版本、参数、finish_reason、响应、usage、解析/过滤结果。门槛：执行的每个案例都输出完整、可解析且有意义的正文/结构；关键事实与来源正确，缺失和冲突不伪造；过滤后句子完整。失败即停止扩大，查根因再重跑；每次重试单独计费和统计。不能从几次成功声称截断率已经达标或专业能力全面合格。

**第三步：定向回归。**冒烟通过后复测 Q08-A、Q15-A、全部 3 组历史对照以及与截断、近期训练/反馈遗漏、计算和引用契约相关的原失败题。Q08-A须完成独立专业复核；Q15-A须无过滤断句且事实与专业内容分别通过。三组历史对照各自需对单变量变化给出相应正确反应，标注每组两条路径的证据及结果；0/3 修复前基线不覆盖或篡改。还要证明实际用户可回答问题不会被控制器误拒，也不能为了降低拒绝率放行错误或不完整答案。

**第四步：同版本全量及独立测试。**在定向问题通过后复测原 34 轮与 6 个历史会话，报告每轮/每请求/每对照组不同分母：完成、截断、解析、控制器接受、语义/事实正确与专业复核分别统计；Q08-A/Q15-A 的最终结论须看复测及专业复核。记录修复前后 token、耗时、真实重试与费用；无 usage 或账单为 NA。再复用既有独立冻结题集或补齐缺口，防止只针对原题修补。

**放行条件**：针对本次报告的 P0 项，专项回归和所覆盖原始用例全部通过；无空正文、截断 JSON 被判为成功；三组历史对照全部通过；关键训练与反馈可沿证据链核对，计算与引用契约冲突均有处理记录。分别报告所有 34 轮控制器结果和经人工核查的语义结果，不能以“全部被控制器接受”代替专业正确，也不得通过关闭拒绝或降低校验门槛制造通过。仍需满足原方案第 7.2 节及测试方案的其他安全、数据、UI 及专业验收条件。任何未测项和失败项均原样保留并标注，未通过则相关功能不放行；具体真实环境发布仍依据已有项目流程。

### 7.3 科学效果验证

先冻结主要评价问题和各方法参数；在授权前提下按时间分开发/留出测试，有条件再留出未见过的用户。比较当前项目已有参考方法、简单滚动参考与本方案：同源同口径、同可得数据、相同 as-of。分别报告稳定性、缺失敏感性、变化识别延迟、用户理解度、分组表现与样本数；连续个体数据按人分析，不能把每天当成完全独立的人。

对“是否帮助判断”，事先定义可核查目标，如后续自报恢复、同条件表现和训练完成；这些是代理终点，不直接等于生物学疲劳真值。若将来要报告状态分数/概率，需要独立评估校准、敏感性、误报漏报与人群外推；若要证明调整建议改善成绩/减少伤病，需要前瞻性对照，不可由相关性推因果。无充分数据就只交付描述与待验证假设。

### 7.4 模型与 UI 评价

复用已有模拟测试的分阶段、小规模方案：优先历史失败，先做低成本连通和身份隔离，再按覆盖缺口调用真实 App 链路；与基线交错对照，冻结题目，补充独立隐藏题。分别报告事实计算、恢复/专业判断、计划、纠错、自然表达、UI/操作、成本及分母；严重错误不能被平均分掩盖。独立专业审核未完成时明确标“待专业复核”，无真实模型或真实设备测试不得声称通过。
