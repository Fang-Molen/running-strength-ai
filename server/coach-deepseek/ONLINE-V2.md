# Online v2 implementation and rollout boundary

This branch implements automatic requests with persistent account-bound permission. It does not deploy, configure an account, reconcile historic spend, or perform a paid model call.

Apply reviewed migrations 001, 002, **003_persistent_online.sql** to the same isolated test database before evaluating the new server. Migration 003 leaves old per-request consents as per-request, removes the one-snapshot-per-consent restriction, and expires old snapshot payloads without deleting history. Set `FANGKUN_COACH_SCHEMA_READY=true` only after the reviewed production migration is separately authorized and applied. The local test uses PGlite SQL with synthetic signed identities and a fake model transport; that is not a production PostgreSQL deployment test.

GET status verifies the actual v3 tables/columns and removal of the one-snapshot consent constraint using read-only schema metadata. The environment readiness flag alone is insufficient: an 002-only database or a rolled-back schema reports `configured:false`, `SCHEMA_MIGRATION_REQUIRED`, and `schemaVerified:false`. This probe performs no authentication, user-record query, model call or ledger reservation; model connection, authorization and billing remain explicitly unverified by GET.

The normal POST snapshot carries `consent.mode=PERSISTENT` and can establish a first authenticated grant. Each grant stores purpose, declared data categories, MODEL service category, disclosure version, authorization basis, creation/expiry/revocation. Subsequent requests reuse it. The server assigns the self-athlete from authenticated identity; submitted records remain USER_DECLARED and never become verified laboratory/device evidence.

`DELETE /api/coach-snapshot` with a snapshot reference revokes only that snapshot. Explicit settings use `POST /api/coach-snapshot {onlineConsent:{enabled:boolean,disclosureVersion:'coach-self-report-v1'}}`. OFF persists a disabled preference and revokes persistent grants. Another device cannot silently re-enable through an ordinary request. Explicit ON is the only re-enable path. Settings and snapshot cleanup remain available with the model disabled when authentication/database infrastructure is available. Failure to reach the server cannot retroactively revoke a delivered provider request; the client retains OFF locally and must show pending server revocation.

Each declared source has a content hash and monotonic generation. New snapshots do not advance unrelated sources, and identical sources do not advance at all. Returning old content advances again instead of reviving old snapshots. Checks run before dispatch and after the response. The dependency map describes only submitted declarations; unsynchronized local edits, deleted sources not sent as changes, and external device facts have not been independently verified by this server. The client must recheck its own selected dependencies before display. This is deliberately not a claim of cross-device authoritative training storage.

Context v2 is a whitelist of 32 records, 24 fields per record, 64 dependencies, 48 KiB maximum. It preserves explicit ACTUAL/PLANNED/TARGET/UNKNOWN states, units, source labels and nullable event/record times. Client identifiers are opaque and ownership is bound to the authenticated self account. Missing dates remain unknown. Server source quotes are reproduced deterministically and compared by the browser. The actual provider envelope has a stricter 4,000/8,000 conservative input bound; oversized context is rejected before budget reservation, never silently trimmed by the server. The selector reports its own omissions.

The selector now budgets actual formatted quote/question/coverage bytes, and an integration test passes a 100-segment historical workout through selector, snapshot HTTP and the real controller with a fake provider. V2 uses its validated structured record contract directly; the legacy brief's 300-character-per-source constraint does not truncate or reject full v2 workout quotations. Personal dependencies choose the 8,000 envelope even if every record is unavailable. An ordinary long question that exceeds the 4,000 envelope may use the existing 8,000 envelope, subject to the same verified per-call cost cap. Neither branch increases configured spending limits.

`coach-assertions-v2` is the same pure classifier in browser and controller. Full declared fact quotations bind personal quantities; explicitly general educational quantities and causal explanations can pass. Invented personal quantities, false writes, diagnosis/clearance, unverified search claims and source promotion fail. It is lexical screening, not professional or semantic certification. A stronger professional evaluator remains unverified. No web search service is wired here: successful model replies report retrieval NOT_REQUESTED.

The classifier accepts optional `question` and scoped `restrictions`. It reconstructs current self-reported symptoms from the question even when the user asks for general knowledge, then checks each affirmative output activity against the restriction's action scope. Current leg pain plus an RPE question permits the RPE explanation, but rejects an unsolicited running clearance. An old lower-body restriction permits unrelated conditional upper-body candidates; a systemic medical restriction still applies to those candidates. The original question's general-knowledge permission does not authorize unrelated exercise advice in the output. Callers without scope information retain the conservative legacy boolean fallback.

The configured policy may allow concurrency 1–32, but no budget value is increased by this change. Existing ledger account caps are immutable through the request path: changing an operator policy without a reviewed corresponding account update returns BUDGET_POLICY_CONFLICT, rather than silently increasing allowance. Unreconciled usage and a full concurrency slot report distinct reasons. Reservation, idempotency, settlement and unknown outcomes remain durable. Error metadata includes stage, dispatchState, ledgerState, traceId and policyVersion; output rejection after provider return reports RETURNED and the actual SETTLED state, never 'not called'. Interrupted/uncertain dispatch is not automatically retried or refunded.

Rollback: stop/hold new API requests, back up the database, and rehearse `003_persistent_online.down.sql` against the backup. It archives consent rows, assigns revoked unique legacy consents to v2 snapshots, and restores the unique constraint while retaining source/preference/audit data. Deploying the old app after this rehearsal requires separately authorized operations. Reapplying 003 restores the new schema but does not restore revoked access. No training, food, body, V4 or user history is deleted by these migrations.

Evidence: `verification/implementation-20261028/online-backend/` contains pre-fix failure, targeted SQL/controller assertions and typecheck output. Existing model answer collections are untouched. No new real model capability result is claimed.
